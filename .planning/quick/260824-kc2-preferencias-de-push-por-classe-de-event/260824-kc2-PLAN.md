<invariante_critico>
**A armadilha central deste plano. O guardião do Task 1 existe para travá-la.**

Hoje o consentimento do `gatilho` é uma CONJUNÇÃO: `persistence.js:479`
(deviceStore `_pushPrefsLocais`) e `:160` (serverStore `syncPushPrefs`) montam
`gatilho: !!(n.enabled && n.gatilho)`, com o comentário em `persistence.js:471`
explicando: *"Consentimento é conjunção — o mestre `enabled` e a classe
`gatilho`; uma classe nova não pode ligar sozinha por cima do interruptor
geral."*

Só que `n.enabled` é o mestre das notificações **LOCAIS** — o `notif` da config
(`App.jsx:4336`: `{ enabled, stop, alvo, agente, variacao }`), disparadas pelo
próprio front. O push server-side de radar/execução/proteção **não consulta
nada** hoje: quem tem token registrado recebe, tenha `enabled` ligado ou não.
Registrar o token é um ato explícito e separado (`onAtivarPush`,
`App.jsx:4375-4381`).

Consequência: aplicar a conjunção `n.enabled && n.execucao` às classes novas
**desliga execução/proteção/radar para todo usuário que registrou push e nunca
ligou o `enabled`** — o oposto exato da decisão travada.

**Modelo de consentimento adotado (escreva o raciocínio no código, nos dois
lados):**

| Mestre | Governa | Onde mora |
|--------|---------|-----------|
| `config.notif.enabled` | notificações LOCAIS do front (stop, alvo, agente, variação) | local, front |
| token registrado (`pushTokens`) | push do SERVIDOR — é o ato explícito de consentimento | kv do servidor |

As classes REFINAM o seu mestre. `gatilho` é a exceção histórica que fica como
está (é conjunção **e** opt-in, porque é a única disparada por evento de
mercado sobre ativo que a pessoa só acompanha) — não regredir.

**Nota a favor, confirmada na leitura do código:** `prefs_for`
(`push.py:91-95`) faz `{**PREFS_PADRAO, **p}`. Prefs já gravadas sem as chaves
novas herdam o default automaticamente — a migração de quem já existe sai de
graça, desde que o default seja o certo. Nenhuma migração de dado é escrita.
</invariante_critico>

<gatilho_intocavel>
**Segundo invariante, achado na revisão do plano. Tem guardião próprio.**

Hoje `serverStore.syncPushPrefs` (`persistence.js:153-161`) NUNCA é chamado —
por isso não existe clobber. No momento em que o web passar a chamá-lo, ele
derivaria `gatilho: !!(n.enabled && n.gatilho)` do `config.notif` **do
servidor**, e para um usuário device-first esse config é o default.

E o default **não é ausência de chave**: `defaults.py:242,247` grava
`"enabled": False` e `"gatilho": False` EXPLICITAMENTE. Como `set_prefs` grava
por chave (`push.py:98-117`), o `gatilho: true` que o iPhone tinha viraria
`false`. Sintoma: o Alex usa o iPhone com gatilho ligado, abre o app no
navegador uma vez, e para de receber aviso de gatilho. Em silêncio.

**Caminho escolhido para fechar (não documentar como limitação):**

> **O `syncPushPrefs` do web manda SÓ as três classes novas.** Nada de
> `gatilho`, nada de `modo`, nada de `universo`.

Por que isto FECHA a janela, em vez de estreitá-la:

1. **É estrutural, não temporal.** O web literalmente não escreve `gatilho` —
   não há ordem de eventos, estado de migração ou "primeiro toque no aparelho"
   que reabra a janela. Um `grep` de ausência prova.
2. **Não custa funcionalidade.** `gatilho` só tem efeito para quem tem token
   APNs, e só o aparelho registra token (`notify.js:338-339`: no web,
   `registerPush` devolve `{ok:false}` antes de qualquer chamada). O `gatilho`
   sempre foi, de fato, preferência do aparelho.
3. **Mantém o comportamento de hoje.** O web já não escrevia `gatilho` (nunca
   chamava a função). Continuar não escrevendo é diff zero de comportamento
   para essa classe.
4. **`modo` e `universo` seguem a mesma regra pela mesma razão.** `modo` já é
   sincronizado pelo aparelho (`persistence.js:640`); `universo` sai da
   watchlist LOCAL do aparelho (`putWatchlist`, `:672-679`, não chama a API), e
   o web tem a watchlist do servidor, que pode ser outra. Escrever qualquer um
   dos dois seria a mesma classe de clobber, com sintoma mais discreto.

**Autoridade, escrita no código dos dois lados:**

| Chave | Quem escreve | Por quê |
|-------|--------------|---------|
| `radar`, `execucao`, `protecao` | os DOIS clientes | controle da conta; o web mostra os mesmos controles |
| `gatilho` | só o aparelho | só o aparelho tem token; `config.notif` local é a fonte |
| `modo`, `universo` | só o aparelho | derivados de estado local-first (appMode, watchlist) |

**Efeito colateral conhecido, bounded, que vai para o SUMMARY:** `set_prefs`
sempre carimba `at`, então um patch só-de-classes renova a validade de 7 dias
do `universo` (`universo_valido`, `push.py:120-133`). Consequência real: conta
ativa no web mantém válido o universo que o aparelho gravou. Não é perda de
segurança relevante — o universo em si não é sobrescrito, e aparelho que sumiu
tem o token descartado pelo próprio APNs (`_DROP_TOKEN_REASONS`, `push.py:161`).
Não invente mudança de semântica do `at` para isto.

**Limitação de produto, status quo, também para o SUMMARY:** ligar/desligar
`gatilho` pelo web não altera o push (altera só `config.notif` no servidor).
Já era assim antes desta entrega. Fechar isso exigiria decidir quem é a fonte
da verdade do `config` num app local-first — decisão de arquitetura, não de
quick task.
</gatilho_intocavel>
