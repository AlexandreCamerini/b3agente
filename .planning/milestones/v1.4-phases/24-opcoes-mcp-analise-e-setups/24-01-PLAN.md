**3. `_em_reais(dados, lote)` — helper PURO (D-24.2).**

```python
def _em_reais(dados: dict, lote: int) -> dict:
    """Cifras da estrutura multiplicadas pelo lote, em reais.

    `lote` é número de AÇÕES: o serviço devolve tudo por unidade do objeto
    (uma ação), e o contrato padrão da B3 são 100 ações. Multiplicar é a
    única conta que esta camada faz, e ela é fechada aqui para não haver uma
    segunda versão dela no front.

    **Breakeven não está aqui, e não é esquecimento:** breakeven é PREÇO DO
    OBJETO, não dinheiro da posição. Multiplicado pelo lote viraria um número
    sem significado que a tela exibiria como reais.

    `None` entra e `None` sai — ganho ilimitado (`max_gain: null`) não pode
    virar 0, que a tela leria como "não ganha nada".
    """
```

Retorna
`{"lote": lote, "custoLiquido": ..., "ganhoMaximo": ..., "perdaMaxima": ...,
  "cenarios": [{"name": ..., "underlying": ..., "resultado": ...}, ...],
  "unidade": "reais para o lote informado (lote = número de ações)"}`.

Regras: `x * lote` só quando `isinstance(x, (int, float)) and not
isinstance(x, bool)`; senão `None`. `cenarios` sai de
`dados["scenarios"]["scenarios"]` quando existir (cada item vira
`{name, underlying (verbatim, NÃO multiplicado — é preço), resultado (×lote ou None)}`);
lista vazia quando não houver. `lote` inválido nunca chega aqui — quem valida
é a rota.

**4. `_lote(body)` — validação (D-24.3).**

```python
def _lote(valor) -> int:
```

**2. `POST /possibilidades` — custo 1 + 2×N (D-24.1).**

Corpo: `{ticker, direction, kind?, lote, alvo?, stop?, expirations?}`.

N_MAX_VENCIMENTOS = 6   # [R-13]: o custo 2xN+1 cresce linear; 6 é o teto que

Fluxo, literalmente:

```python
with _cap_check(uid, 1) as cap1:
    base, _c = await _chamada_com_cap(cap1, "propose_option_setups", {"ticker": alvo})
    disponiveis = [v for v in (base.get("expirations") or []) if isinstance(v, str)]
    escolhidos = (pedidos or disponiveis)[:N_MAX_VENCIMENTOS]

    # de sobra; reservar 1 e gastar 13 mentiria o cap (D-24.1).
    with _cap_check(uid, 2 * len(escolhidos)) as cap2:
        for venc in escolhidos:
            ...
```

`pedidos` = `body.get("expirations")` quando for lista de strings, senão
`None`; os pedidos são intersectados com `disponiveis` (vencimento que a
cadeia não tem não vira chamada). `escolhidos` vazio → resposta 200 com
`possibilidades: []` e `motivo` dizendo que não há vencimento aberto — sem
entrar no segundo `with` (reservar 0 é no-op por construção de `_cap_check`).

Por vencimento, em sequência (o `mcp_client` já limita concorrência com
`Semaphore(4)`; aqui a ordem importa para o cap ser contado uma vez por
chamada):

1. `propose_option_setups` com `{ticker, direction, kind?, expiration}` →
   pega `setups[0]` quando existir.
2. Com as pernas de `setups[0].legs` (campos `contract`/`side`/`quantity`),
   `evaluate_option_structure` com
   `{"ticker": alvo, "legs": [...], "scenarios": cenarios}`, onde `cenarios`
   são os extras nomeados: `[{"name": "alvo", "underlying": alvo_preco}]` e/ou
   `[{"name": "stop", ...}]`, omitidos quando não vieram. A banda ±1σ o
   serviço já devolve sozinho.

Estrutura que não montou (`setups: []`): entra na lista com
`{"vencimento": venc, "estrutura": None, "motivo": <reason verbatim>}` e
**pula a segunda chamada** — avaliar o que não existe gastaria cap por nada.
Consumir menos que o reservado é sempre permitido, e o saldo volta na saída.

Erro de tool em UM vencimento NÃO derruba os outros: captura
`mcp_client.McpErroDeTool` dentro do laço, registra
`{"vencimento": venc, "estrutura": None, "erro": str(e)}` e segue. As demais
exceções (`McpNaoConfigurado`, `McpNaoAutorizado`, `McpIndisponivel`,
`McpTetoAtingido`, `ValueError`) são condição do SERVIÇO, não daquele
vencimento: propagam para `_erro_http` e encerram a rota — insistir nos
outros cinco vencimentos contra um serviço fora do ar só queima a viagem.
