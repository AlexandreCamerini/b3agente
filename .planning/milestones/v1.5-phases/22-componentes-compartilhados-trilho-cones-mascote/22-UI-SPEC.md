### Out-of-scope symbols (do NOT touch under SYS-02)

The broader Unicode sweep also matched a large number of `→ ✓ ✗ ✕ ↻ ✎ ⚠ ⚡
↔ ↺ ↓` occurrences throughout `App.jsx` and `copy.js`. These are **not**
"emoji nativo do sistema operacional" in the sense `REQUIREMENTS.md` SYS-02
targets — they are the app's own established monochrome typographic
vocabulary (arrows in copy prose, `✓`/`✗` status glyphs in `copy.js`
microcopy, `↻` refresh / `✎` edit / `✕` close used as inline button glyphs
throughout, `⚠` warning inline with `T.negative` coloring, `⚡` lightning
already manually recolored via `T.accent`). None of these render as
colorful pictographs by default the way `🎓/📈/✨/✅/📡`/circle-tier-dots do,
and several (`↻`, `✎`, `✕`) are already de facto "the icon system" this
phase's `NavIcon`-style SVGs are meant to formalize. Converting all of them
to SVG would be a much larger, unscoped rewrite of the app's inline
copy/microcopy — explicitly out of bounds per `22-CONTEXT.md`'s "Fase de
unificação, não de criação de novo padrão visual." **SYS-02's scope is the 6
glyph families in the table above, nothing else.**

### Flagged exception — tier-dot fill (SYS-02, line 6926) — approved, see Decisions

`tierOf()` (`App.jsx:963-969`) was written with the explicit design
rationale, in its own comment, that green/red are "reservados a sinal de
mercado" (`T.positive`/`T.negative` = `BRAND.green #34d399`/`BRAND.red
#f26d6d`, used for buy/sell and P&L sign) — so the tier ("Forte/Moderada/
Neutra/Fraca" confluence quality, a *different* semantic axis) deliberately
used the emoji's own built-in color instead of borrowing those tokens.
**Preserve that separation.** Do not reuse `T.positive`/`T.negative`/
`T.warn`/`T.accent` for the new SVG dot — replicating those would silently
reintroduce the exact collision the original author avoided.

Recommended literal (non-`T.*`) fill values, same in both themes (the dot
is decorative and always paired with a mandatory text label — `6926`
already renders `{dot} {label} · aderência ao padrão de estudo`, so no
theme-contrast requirement applies the way it does for text or the PetFab
shadow):

| Tier | Fill | Rationale |
|------|------|-----------|
| Forte | `#22c55e` | Distinct hue from `BRAND.green` (`#34d399` is teal-leaning; `#22c55e` is pure green) — avoids "this IS the P&L green" misread |
| Moderada | `#f59e0b` | Distinct from `T.warn` (`#fbbf24`/`#a16207`, reserved for daily-log/diário alerts) — same amber family, different shade so it doesn't imply "warning" |
| Neutra | `#9ca3af` | Mid-grey, visible on both `T.bgBase` values (⚪ white would vanish on the light theme's near-white background) |
| Fraca | `#ef4444` | Distinct from `BRAND.red` (`#f26d6d`) |

This is a genuine new-color introduction, flagged because it is the one
place this phase departs from "reuse `T.*`, introduce nothing new." Scope
is exactly 4 literal hex values, used in exactly one call site (`6926`),
never as text color, never reused elsewhere. This has been reviewed and
approved (see Decisions below). If the checker's Color dimension treats any
non-`T.*` hex as a hard fail regardless of context, escalate to the human
before merging — do not silently substitute `T.positive`/`T.negative` to
pass a lint, since that reintroduces the collision this section documents.

## Structural Contract

### SYS-01 — carousel taxonomy: snap is universal, peek-width is NOT — approved, see Decisions

`22-CONTEXT.md` says "aplicar o MESMO padrão" to every non-compliant
trilho, and `REQUIREMENTS.md`'s success criterion #1 says every trilho
should "deixar o próximo item espiando." Read literally, this means copying
HERO-CARROSSEL's exact mechanism — `flex:"0 0 84%", maxWidth:"330px",
scrollSnapAlign:"center"` per item — onto all three non-compliant trilhos.

**Applying that literally would regress two of the three sites:**

- `TECH_MODELS` (`3792`) is an 8-chip filter rail (`minWidth:"118px"` each,
  total row ≈1000px). Forcing each chip to `flex:"0 0 84%"` would show
  ~1.2 chips at a time instead of ~3, turning a "browse all 8 models"
  filter into a one-at-a-time swipe — a real interaction regression for a
  control the user is meant to scan, not focus on one item of.
- `OportunidadesOpcoes` (`4001`) and `PropostaDaPosicao` candidatos
  (`4133`) are `minWidth:"210px"` cards specifically designed to be
  **compared side-by-side** (Fase 19's whole point, MULTI-01/02, is showing
  put-isolada vs. collar together for the user to weigh). Forcing `84%`
  width would hide the second candidate off-screen by default, undermining
  the comparison this exact requirement (Fase 19) was built to enable.

Additionally, HERO-CARROSSEL's peek only works visually because it breaks
out to the viewport edge (`margin:"0 -18px", padding:"2px 18px 6px"` —
bleeds past the page's own side padding). All three non-compliant trilhos
live **inside a bordered `card` div** (`TECH_MODELS` inside the "MODELO DE
ANÁLISE" card; the two options trilhos inside their own container divs with
no page-padding bleed). Applying an edge-to-edge bleed inside an already-
bordered card would visually break through the card's border — not a
"peek," a rendering bug.

**Resolution — split the contract into two behaviors, both satisfying
"the user always perceives more content," neither regressing existing UX:**

1. **Universal (applies to all 3 non-compliant trilhos):** add
   `scrollSnapType:"x proximity"` to the container and `scrollSnapAlign:
   "start"` to each item. `proximity` (not `mandatory`) because these are
   multi-item browse/compare rows, not one-at-a-time focus carousels —
   `mandatory` would fight free scrolling across many short chips or force
   an awkward stop mid-comparison. This satisfies "rola com snap" for
   every trilho without changing any item's width.
2. **Peek is already present by construction for these 3, once snap
   is added** — `TECH_MODELS` chips (118px×8, gap 8px) and the options
   cards (210px minWidth, gap 10px) are already narrower than the
   viewport, so a partial next item is already visible today (the missing
   piece was never "no peek," it was "the scroll doesn't settle onto an
   item boundary," which step 1 fixes). No `flex`/`maxWidth` change to any
   of these 3 sites' items.
3. **HERO-CARROSSEL (`1949`) is unchanged** — it already is the "one
   dominant card + peek" pattern; it stays the canonical example of that
   sub-variant, used only where a single dominant focal card is the right
   interaction (home setups). No other trilho in the current sweep needs
   that sub-variant.

**Shared helper, per `22-CONTEXT.md`'s Claude's Discretion (name is
implementer's choice) — recommended shape:**

```js
// carouselTrackStyle(extra) — base for every horizontal-scroll container.
// extra: object merged last, for call-site-specific gap/margin/padding.
const carouselTrackStyle = (extra) => ({
  display: "flex",
  overflowX: "auto",
  scrollSnapType: "x proximity",
  WebkitOverflowScrolling: "touch",
  ...extra,
});
// carouselItemStyle(align) — base for every scrollable item.
// align: "start" (browse/compare rows) | "center" (single-focus HERO-style).
const carouselItemStyle = (align = "start") => ({ scrollSnapAlign: align });
```

Call sites merge their own `gap`, `minWidth`/`flex`, `margin`/`padding` on
top — this helper only carries the parts that were actually divergent
(snap behavior), not every style property, so it doesn't force call sites
into identical visual density.

**Minor cleanup while touching these 3 sites:** `4001` and `4133` set
`scrollbarWidth:"none"` (Firefox-only, hides the scrollbar); `1949` and
`3792` do not. The global `.b3 ::-webkit-scrollbar` rule (`App.jsx:340-341`)
already styles a thin 10px custom scrollbar for WebKit — keep that
consistent across all 4 trilhos (do not add `scrollbarWidth:"none"` to the
2 that lack it, and optionally remove it from the 2 that have it, for one
uniform scrollbar treatment). Not required by any named requirement; flag
for planner as a low-cost consistency fix, skip if it risks scope creep.

**Verification:** `grep -n "scrollSnapType" web/src/App.jsx` must return 4
matches after this phase (was 1). `grep -n "flex: \"0 0 84%\"" web/src/App.jsx`
must still return exactly 1 match (HERO-CARROSSEL, unchanged) — if it
returns more than 1, the peek-width mistake described above was made.

### SYS-03 — PetFab shadow becomes theme-aware — approved as starting value, see Decisions

**Current code, verified (`App.jsx:2748-2755`):**
```jsx
<button onClick={onOpen} aria-label="Abrir o assistente Boris+"
  style={{ position: "fixed", right: "14px", bottom: "92px", zIndex: 60, width: "54px", height: "54px", ... }}>
  <div aria-hidden style={{ lineHeight: 0, filter: "drop-shadow(0 3px 6px rgba(0,0,0,0.45))" }}>
    <Boris size={40} />
  </div>
</button>
```
The shadow already exists (added 2026-08-08 per the component's own
comment — "a sombra saiu do círculo e foi para a SILHUETA") but is a
**hardcoded `rgba(0,0,0,0.45)`**, identical in both themes — exactly the
pattern `22-CONTEXT.md` says to stop doing ("nunca um hex fixo que só
funciona num tema").

**Add a new token pair to `PALETTE`** (`App.jsx:61-172`), following the
exact literal-rgba convention `scrim` already uses at lines `80`/`106`:

```js
// PALETTE.dark, alongside the existing scrim entry:
shadowFab: "rgba(0,0,0,0.45)",   // current value, unchanged — dark theme keeps today's look
// PALETTE.light:
shadowFab: "rgba(15,20,28,0.22)", // lighter/less opaque — a 0.45-opacity black halo on the
                                   // light theme's near-white bgBase (#f7f8fc) would read as a
                                   // heavy dark smudge, not a subtle separation halo; the
                                   // existing light-theme `scrim` (rgba(15,20,28,0.45)) is
                                   // calibrated for a full-screen overlay, too strong for a
                                   // small drop-shadow — 0.22 is the approved starting point;
                                   // see Decisions below for the required live visual check
                                   // before considering SYS-03 done.
```

Call site becomes:
```jsx
<div aria-hidden style={{ lineHeight: 0, filter: `drop-shadow(0 3px 6px ${T.shadowFab})` }}>
```
`T.shadowFab` resolves through the existing `T = Object.fromEntries(...)`
mechanism (`App.jsx:113`) automatically — no change needed to that
machinery, only to `PALETTE.dark`/`PALETTE.light` and the one call site.

**Verification (human, both themes):** open any screen where a card sits
directly under the FAB's fixed position (bottom-right, `right:14px,
bottom:92px`) in both dark and light theme. The halo must visibly separate
the owl's silhouette from the card behind it without producing a visible
"disc"/badge shape around the art (the PNG already has its own transparent
edge — the shadow should read as depth, not a background shape). This is
inherently a visual judgment call, not something a unit test can verify —
flag as a human-check step in the phase's plan, same as Phase 20/21's
visual calibration steps.
