# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note — read this first

This phase closes 11 REPORT-01 Médio findings (FIX-C21..C27, C33, C34, C38,
C39), of which **8 have zero rendered UI** (CODE/test/guardian work) and
**1 (C-39) is a data-model change with zero rendered UI**. Only **2 findings
touch pixels**: C-23 (`web/src/App.jsx`) and C-38 (`web-admin/src/App.jsx`).
This spec is intentionally small — it points at exact existing patterns to
reuse, not new design.

**Two separate codebases, two separate token systems** — neither uses
shadcn/Tailwind; both are hand-rolled React with inline `style={}` objects
reading from a `T` token object:

| Project | Token source | Theme |
|---------|-------------|-------|
| `web/src/App.jsx` (consumer app) | `PALETTE.dark`/`PALETTE.light` + `MODE_OPERADOR` override, exposed as CSS vars via `T` (line ~113) | Two axes: theme (dark/light, follows OS) × mode (Estudo/Operador, changes accent only) — Brand Book v2 |
| `web-admin/src/App.jsx` (admin portal) | Flat `const T = {...}` object (line 14) | Dark-only, gold accent `#d4af37`, no theme switch |

Do not port tokens between the two projects. Do not introduce shadcn,
Tailwind, or a new component library in either — out of scope, and would
contradict "mechanical fix" framing of both requirements below.

## Component Contracts (by requirement)

### FIX-C23 — Toggle `disabled` (web/src/App.jsx) — the only real component change

**Current state:** `Toggle({ on, onClick, label })` (line 328) has no
`disabled` prop. The "Entrada automática" master toggle (line 4240) gates
its *effect* in the `onClick` handler (`() => operador && putAg(...)`) but
renders as a fully-interactive, fully-opaque control even when
`operador === false` — clickable-looking, keyboard-focusable, no dimming.
Compare with the **already-correct** sibling controls on the same screen:
`allocPct` slider (line 4247, `disabled={!operador}`, section wrapped in
`opacity: operador ? 1 : 0.6` at line 4242) and the "Executar" segmented
button (line 4104, `disabled={desabilitado}`, `opacity: desabilitado ? 0.6 : 1`,
`cursor: desabilitado ? "not-allowed" : "pointer"`).

**Contract:**
1. Extend `Toggle` signature to `Toggle({ on, onClick, label, disabled })`.
2. Apply `disabled={disabled}` to the underlying `<button>` (real HTML
   attribute — this is the entire point of C-23, not a cosmetic add-on).
3. Visual dimming: wrap the button's existing computed style with
   `opacity: disabled ? 0.6 : 1` and `cursor: disabled ? "not-allowed" : "pointer"`
   — identical numeric values already used by the Executar button and the
   allocPct section, do not invent a different dimming factor.
4. `aria-checked`/`aria-label` stay as-is (already present); add nothing new
   there — `disabled` alone is sufficient for assistive tech to announce
   the state correctly once the real attribute exists.
5. At the call site (line 4240): `<Toggle on={!!ag.entradaAuto && operador} disabled={!operador} onClick={() => operador && putAg({ entradaAuto: !ag.entradaAuto })} label="Entrar automaticamente" />`. The `onClick` guard (`operador &&`) can stay as defense-in-depth even after `disabled` makes it unreachable via pointer/keyboard — do not remove it, no regression risk either way.
6. Do **not** touch color: a disabled `Toggle` must still use its existing
   `on`-based color logic (`s.bg`/`s.border`/`s.knob`/`s.color`, line 329) —
   only opacity/cursor/HTML-attribute change. This keeps the "off" visual
   identical to today (since `operador === false` already forces `on=false`
   in practice), so there is no color regression to verify.
7. No copy change — the explanatory paragraph two elements below (lines
   4253-4260) already exists and already says the right thing.

**Full visual weight requirement (product principle, CLAUDE.md item 9):**
the disabled state must remain clearly legible, not vanish — `opacity: 0.6`
(not lower) matches the existing precedent exactly and keeps the control
readable, consistent with "não manipular/diminuir estados negativos."

### FIX-C38 — Preventive spend alert (web-admin/src/App.jsx)

**Current state confirmed by reading `metering.py`:** the hard stop
(`cap_global`, checked in `check()`, line 102) is a threshold comparison
with **no configurable warning band** — it either allows or rejects, no
intermediate state exists today. The existing "alert-with-threshold" visual
precedent this section relies on is `data.candles.vazios`
(`candle_provider.py:140-141`, rendered `web-admin/src/App.jsx:189`,
`tone="warn"`) — a **hardcoded module constant** (`_LIMIAR_ERRO`), not an
admin-editable value. (The adjacent `Kv` at line 191, `alerta`, is a
different field with `tone={alerta ? "negative" : "positive"}` — not part of
this precedent, cited here only to avoid confusing the two.) That precedent
is the right one for the *display* half of C-38 but
the WRONG one for "configurável." The correct precedent for the
*configuration* half is `_CONFIG_IA_CAMPOS` / `admin_config_ia_get`/`put`
(`server/app/main.py:693-729`) + the `MudancaDeLLM` component's `campo()`
helper (`web-admin/src/App.jsx:641-649`) — this is how this exact codebase
already lets an admin edit a numeric IA-related limit with permission gating,
an audit trail, and a save button, without inventing a new pattern.

**Contract — read side (Custos tab, "Uso de IA" card, `web-admin/src/App.jsx:154-168`):**
1. Add one `Kv` row directly after the existing `EventoComSerie` "Tokens/dia"
   row (after line 161), same card, same visual rhythm as every other row
   in this card — no new container, no new card.
2. Label: `"Alerta de gasto (IA gerenciada)"`.
3. Value: mirror the exact string shape at line 191
   (`"⚠ acima do limiar de X%" : "dentro do normal"`), reworded per the
   Copywriting Contract above.
4. `tone`: `"warn"` when the preventive threshold is crossed, `"positive"`
   or `undefined` when not (same `tone` vocabulary already used everywhere
   in this file — `Kv`'s `tone` prop already supports `warn`, no new prop
   needed). Never `"negative"` for the preventive alert — reserve
   `"negative"` for if/when the read reflects the hard stop itself (a
   separate, already-existing signal, `analisesGerenciadas` cap reached).
5. If no threshold is configured (field empty/null), value reads
   `"não configurado"` in `T.faint` (no `tone`) — same "no override set"
   treatment `campo()` already implies for empty config fields (line 686-690
   placeholders), so an unconfigured alert never looks like a false "all
   clear" positive/warn state.

**Contract — write side (`MudancaDeLLM` component, `web-admin/src/App.jsx:627-706`):**
1. Add two new fields to `_CONFIG_IA_CAMPOS` (backend, `main.py:693`) and
   two matching `campo(...)` calls in `MudancaDeLLM` (after the existing
   `llmGlobalDailyCap` field, line 690) — same `campo()` helper, same
   `numerico={true}` (opens numeric keyboard, ADR-014 mobile requirement),
   same `disabled={!podeEditar}` gating on `llm.configurar` permission,
   same "Salvar (auditado)" button and audit-log write path. Zero new UI
   pattern — literally two more calls to a function that already exists.
2. Field labels/placeholders: per Copywriting Contract above.
3. No new permission — reuse `llm.configurar` (same permission that already
   gates every other IA-config field on this same card).

**Explicitly out of scope for C-38 (per 05-CONTEXT.md):** push/e-mail
delivery of the alert — visual indicator only, same reduced-scope precedent
C-37 already set in Phase 3.

### FIX-C39 — Auditoria tab `perm` field (web-admin/src/App.jsx) — NOT a visual change

**Verified by reading the code:** `perm` (`VIEWS` array, lines 1199-1208) is
**never rendered anywhere** — its only consumer is the filter predicate
`VIEWS.filter((v) => !v.perm || perms.includes(v.perm))` at line 1274. There
is no tab-bar badge, tooltip, or label that displays a permission string to
any user today. "Alinhando com o padrão visual das outras 9 abas" in
05-CONTEXT.md refers to the **source-array shape being self-documenting**
(every entry declares its access rule explicitly), not to any pixel a user
sees. **The checker should not expect a rendered UI element for this
requirement** — flag it as a false positive if one is requested.

**Contract — the exact change required, so the executor doesn't invent a
real permission string that silently narrows access (05-CONTEXT.md is
explicit: the access rule must stay "any admin permission," unchanged):**

1. Declare a sentinel constant near `VIEWS`: `const PERM_ANY = "*";` with a
   one-line comment: `// sentinel: nenhuma permissão específica exigida —
   qualquer permissão administrativa basta (mesma regra de hoje).`
2. Set the Auditoria entry to `{ id: "auditoria", label: "Auditoria", C: Auditoria, perm: PERM_ANY }`.
3. Update the filter to treat the sentinel identically to "no perm":
   `const visiveis = VIEWS.filter((v) => !v.perm || v.perm === PERM_ANY || perms.includes(v.perm));`
4. Do **not** assign a real permission string (e.g. `"observabilidade.ver"`)
   to Auditoria — that would be a genuine access-rule change, explicitly
   forbidden by the C-39 decision in 05-CONTEXT.md, and backend already
   gates the route with `require_any_admin_permission()` independently (no
   vacuum if the front-end filter is inert).
5. No visual/copy verification needed beyond confirming the tab still shows
   for every admin permission combination it showed for before (regression
   check, not a new-state check).
