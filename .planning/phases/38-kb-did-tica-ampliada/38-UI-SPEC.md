## Design System

| Property | Value |
|----------|-------|
| Tool | none — custom inline-style token system, not shadcn |
| Preset | not applicable |
| Component library | none — hand-rolled React components in `web/src/App.jsx` |
| Icon library | none — inline hand-authored SVG (24x24 viewBox, `stroke="currentColor"` strokeWidth 2, round linecap/linejoin), same shape as `NavIcon`/`ProfileTile` icon slot (`web/src/App.jsx:2473-2482`) |
| Font | Display/headings: `DISPLAY = "'Fredoka', " + SANS` (`App.jsx:293`). Body/UI: `SANS = "'Nunito', -apple-system, system-ui, 'Segoe UI', Helvetica, Arial, sans-serif"` (`App.jsx:291`). Numeric/monospace (counts, prices): `MONO` (`App.jsx:286`) |

**No shadcn gate applies.** `components.json` confirmed absent (`test -f components.json` → not found, repo-wide). This is NOT a fresh React/Vite scaffold — it is a 7600+ line mature `App.jsx` with its own CSS-variable token system (`PALETTE.dark`/`PALETTE.light` → `T.*`, `App.jsx:99-216`), used consistently across 37 prior phases. Introducing shadcn here would fork the design system mid-project, contradicting the repo guardrail "não reescreva a aplicação sem necessidade" (`CLAUDE.md`). Every UI-SPEC for this repo to date (Phases 32, 34, 35 — see `.planning/STATE.md`) made the same call: reuse the existing token system, sign exceptions instead of normalizing. This phase follows that precedent.

## Spacing Scale

Declared values (project convention — not the generic 4px grid; matches the scale already in continuous use across `ProfileTile`, `ConceitoSheet`, `field`, `card`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 6px–8px | Icon-to-label gap, chip internal gap |
| sm | 9px–10px | Compact element spacing (input padding, tile icon gap) |
| md | 12px–14px | Default element spacing (card padding, list row padding) |
| lg | 16px–18px | Section padding (`ConceitoSheet` body padding is `16px 18px`) |
| xl | 24px | Layout gaps between major blocks |

**Exceptions — developer-approved, matches existing pattern** (same standing approval as `32-CONTEXT.md`, 2026-09-15, and `35-CONTEXT.md`, 2026-09-21, both citing `file:line`): this codebase does not use a strict 4px grid. `ProfileTile` uses `padding: "14px"`, `gap: wide ? "13px" : "9px"` (`App.jsx:2474`). `field` uses `padding: "10px 11px"` (`App.jsx:365`). `ConceitoSheet` uses `padding: "16px 18px calc(18px + env(safe-area-inset-bottom))"` (`App.jsx:2941`). New components in this phase (search tile, search screen, result rows, family accordion) MUST reuse these exact declared values — not introduce a new 4px-grid scale that would visually clash with the screens the user navigates to/from (Perfil hub, the 4 tabs receiving "saiba mais" links).

## Typography

Reused from existing `ProfileTile`/`ConceitoSheet` conventions — no new sizes or weights introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Screen heading (glossary screen title) | 18px | 800 | 1.2 (matches `ConceitoSheet` `h2`, `App.jsx:2941`) |
| List item title / tile title | 13.5px | 700 | 1.4 (matches `ProfileTile` title, `App.jsx:2477`) |
| Body / verbete text | 13.5px | 400 | 1.6 (matches `ConceitoSheet` paragraph, `App.jsx:2955`) |
| Meta / subtitle / family label | 11.5px | 400 | 1.4 (matches `ProfileTile` sub, `App.jsx:2478`) |
| Kicker (uppercase section label, e.g. family accordion header) | 10px | 800, `letterSpacing: "0.08em"`, `textTransform: "uppercase"` | 1.2 (matches `hubGroup`, `App.jsx:2482`, and `ConceitoSheet` block labels, `App.jsx:2952`) |

Weights used: **700** (semibold — titles, CTAs, active states) and **800** (extrabold — headings, kickers, buttons). Body copy uses 400. This is 3 weights total, matching the standing exception already signed in `32-CONTEXT.md`/`35-CONTEXT.md` for this codebase (never renegotiate the base scale inside a feature phase — normalization is out of scope here, same reasoning as those two).

## Phase-Specific Component Contract

*(Extends the template with concrete states this phase needs — downstream: `gsd-planner` translates these into tasks, `gsd-executor` implements against them, `gsd-ui-checker`/`gsd-ui-auditor` validate against them.)*

### 1. Glossary tile in Perfil (KB-01 entry point)

- Reuses `ProfileTile` **verbatim** (`App.jsx:2473`, `wide=false` grid-cell variant, same as "IA & Boris"/"Eficiência da IA" siblings at `App.jsx:2732-2751`) — no new tile component.
- Icon: single hand-authored SVG (book/glossary glyph), same 24x24 stroke convention as sibling tile icons.
- Placement: inside the existing `hubGrid` (`App.jsx:2483`) alongside the other secondary tiles — not `wide` (not full-width), since it is a peer of "IA & Boris"/"Notificações", not of "Conta"/"Preferências".

### 2. Search + family navigation screen (KB-01)

- Opens as a focused sub-screen from the tile (same navigation pattern as `onOpen("config")`/`onOpen("ia")`, `App.jsx:2726-2751`) — not a modal/sheet.
- **Layout, top to bottom:** screen heading → search input (sticky-adjacent, not floating) → results.
- **Search input:** reuses `field` token (`App.jsx:365`) at full width. Live filter, fires on every keystroke, no debounce, no minimum character count — D-04 mandates this is a synchronous filter over an in-memory array already fetched once (at most 83 items; no performance case for debouncing). No loading spinner ever appears while typing.
- **Clear affordance:** an inline "×" button appears inside the field once the value is non-empty, clearing the field and returning to the family-accordion view. This is a new but low-risk addition — reuses the field's existing border-radius/height, adds a plain-transparent-background button sized to the field's interior height (no new visual token needed).
- **Three mutually exclusive result states**, selected by field state + result count:
  1. **Empty query** → family accordion (9 sections: `indicadores`, `estrutura`, `familias`, `modelos`, `setups`, `plano_risco`, `fundamentos`, `mercado_b3`, `estados_app`) — each section header uses the Kicker typography role, each row inside uses the List item title role. Collapsed by default; tapping a header expands/collapses (no navigation).
  2. **Non-empty query, 1+ matches** → flat filtered list (D-03: no result cap), same row component as the family accordion's rows, no section grouping.
  3. **Non-empty query, 0 matches** → empty-state copy (above) rendered ABOVE the still-visible, still-interactive family accordion — never a full-screen empty illustration that replaces navigation.
- **Result row:** tapping any verbete (from either the accordion or the filtered list) opens the same `ConceitoSheet` already used app-wide (`App.jsx:2941`) — not a new detail screen.

### 3. "Saiba mais" links in the 4 uncovered tabs (KB-02)

Fixed `vid` per tab — proposed here per `38-CONTEXT.md` D-08 ("proposta do planner... revisada e aprovada pelo Alex antes de qualquer código"; researcher proposes with citation, planner carries it into the plan for that approval):

| Tab | Proposed `vid` | Família | Justification (file:line) |
|-----|----------------|---------|----------------------------|
| Acompanhar (`evolucao`) | `mkt-carteira-simulada` | `mercado_b3` | `EvolucaoScreen` (`App.jsx:2057`) is the home dashboard of the simulated portfolio — equity curve, patrimônio, day P&L (`App.jsx:2070-2072`). This verbete is literally "o que é a carteira simulada" (`server/app/kb.py:1219-1235`) — it also reinforces CLAUDE.md princípio 1 (saldo fictício sempre visível) directly on the screen the user opens first |
| Radar | `confluencia` | `setups` | `RadarScreen` (`App.jsx:6678`) ranks/screens the market by confluência entre famílias — the mechanic IS the verbete. `confluencia` already exists as a `kb.py`-derived concept mapped to família `setups` (`server/app/kb.py:83`), same concept `MercadoScreen` sorts by (`App.jsx:3878`) |
| Watchlist (`mercado`) | `ind-rsi` | `indicadores` | `MercadoScreen` (`App.jsx:3853`) is fundamentally about reading technical indicators per ticker; RSI is the single most recognized beginner-facing indicator in the `indicadores` família (`server/app/kb.py:169`) — best single entry point for "o que é um indicador técnico" |
| Opções | `mkt-opcao` | `mercado_b3` | The entire tab is about options; `mkt-opcao` (`server/app/kb.py:1197`) is the foundational "o que é uma opção" definition — necessary before any of the tab's structures (venda coberta, put, collar) make sense to a first-time reader |

Each link: same visual treatment as the existing Portfólio link (`App.jsx:4358` — transparent background, no border, `T.accent` text, 700 weight, 12px, no underline) and same `A.abrirVerbete(vid, dados)` call pattern (`App.jsx:8624`) — not `A.abrirSetor` (would pollute `gestoUso` telemetry, per the comment at `App.jsx:8619-8623`).

**Placement per tab is NOT specified here** — that is a layout decision for the plan (where exactly in `EvolucaoScreen`/`RadarScreen`/`MercadoScreen`/`OpcoesScreen` the link sits), constrained only by: must not compete visually with the primary veredicto/CTA of each screen, and must follow the same "one generic line, not a banner" footprint as the Portfólio precedent.

### 4. `ConceitoSheet` rendering a `kb.py`-sourced verbete — contract, not implementation

`ConceitoSheet` today expects `{titulo, oQueE: [...], oQueAcontece: [...], naoAcontece: [...], veja: [...]}` (`conceitos.montar()` shape, consumed at `App.jsx:2955-2969`). `kb.formatar()` returns a DIFFERENT shape: `{id, familia, texto: "<single paragraph>", veja: [...]}` — no `titulo`, no 3-way block split (`server/app/kb.py:1618-1628`). This is a real data-shape gap, not a cosmetic detail, and it is EXPLICITLY implementation territory per `38-CONTEXT.md` ("Claude's Discretion" — "não vai a discuss-phase... mas o researcher/planner DEVE endereçar isso explicitamente"). This UI-SPEC's job is to constrain the VISUAL result, not design the bridge:

- A kb-sourced verbete opened in `ConceitoSheet` MUST still show a heading (reuse the 18px/800 Screen-heading role) — if `kb.formatar()` has no `titulo`, the plan must decide where that heading text comes from (candidates: add `titulo` to `kb.py`'s verbete dict — the more honest fix, since `conceitos.py`-derived verbetes already have one via `c["titulo"]`; or derive a display label client-side from `termos[0]`). **This UI-SPEC does not pick between those — that decision belongs to the plan**, but whichever is chosen, the heading role/size/weight above is non-negotiable.
- The single `texto` string renders as ONE paragraph block using the Body typography role — it does NOT need to be force-split into the `naoAcontece`/`oQueE`/`oQueAcontece` three-block layout. Do not invent placeholder empty blocks to force parity with the `conceitos.py` shape.
- `veja` navigation (the pill-chip "veja também" row, `App.jsx:2975-2987`) renders identically regardless of source — both shapes carry `veja: list[str]`, and both are validated as link-safe by the same "todo id citado aqui EXISTE no catálogo" guarantee (`server/app/kb.py:35-36`).
- The existing `AssistenteBox` ("Pergunte à IA sobre estes números", `App.jsx:2865`) is untouched — kb-sourced verbetes have no `dados` payload (they are static glossary entries, not per-ticker readings), so the assistant box either doesn't render for kb-only opens or renders with an empty snapshot; this is again a plan-level wiring decision, not a visual one — visually, if shown, it is byte-identical to today's box.
