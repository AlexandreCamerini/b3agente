# Phase 19 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** this phase does NOT introduce a new visual language. Per
`19-CONTEXT.md` (MULTI-02), the N-candidate picker inside `PropostaDaPosicao`
(`web/src/App.jsx:3992-4060`) reuses the exact card/horizontal-scroll pattern
already shipped in `OportunidadesOpcoes` (`web/src/App.jsx:3919-3981`, Phase
18). This spec documents that existing pattern verbatim (so planner/executor
implement against real values, not invented ones) and resolves the two
genuinely open interaction questions CONTEXT.md left unanswered.

## Spacing Scale

**Deviation from the template's 8-point scale, declared openly:** the actual
shipped card pattern this phase extends uses a denser, non-4px-multiple
increment set (3/4/6/8/9/10/11/14/16px), inherited verbatim from Phase 14
(`PropostaLastreada`) and Phase 18 (`OportunidadesOpcoes`, `PropostaDaPosicao`).
This is NOT introduced by Phase 19 — it is the pre-existing contract of the
component being extended. Do not round these to a clean 4px grid; matching
the sibling card exactly is the requirement (MULTI-02: "mesmo padrão visual").

| Token | Value | Usage (as coded today) |
|-------|-------|-------------------------|
| 2xs | 2px | eyebrow-to-value micro gap (`marginTop: "2px"`, manchete under eyebrow) |
| xs | 3–4px | icon-to-label gap, eyebrow-to-ticker gap |
| sm | 6–8px | chip gap (`gap: "8px"`), payoff-row internal gaps |
| sm+ | 9–11px | card internal padding (`padding: "10px"` payoff box, `"11px 12px"` tira item, `"16px"` full card padding) |
| md | 14px | section bottom margin (tira container `marginBottom: "14px"`) |
| Candidate item min-width | 210px | `minWidth: "210px"` on each scrollable item — reuse unchanged |
| Touch target | 44px | `minHeight: "44px"` on tappable card items (accessibility floor, reuse unchanged); CTA buttons use `minHeight: "40px"` (existing exception, also reuse unchanged) |
| Card radius | 9–11px | `borderRadius: "9px"` (chips/payoff box), `"11px"` (card/tira item) |

Exceptions: entire scale is an exception to the template's 8-point default —
see deviation note above. Do not introduce a THIRD spacing convention for
the new N-candidate row; reuse these values exactly.

| Role | Value (dark theme, as coded) | Usage |

| Dominant (60%) | `T.bgBase` = `#10121a` | Screen background, payoff sub-box background |
| Secondary (30%) | `T.bgCard` = `#1b1f2e` | Card surface (each candidate item, the proposal panel) |

CTA border/background uses `T.accent`/`T.accentTint` (existing exception for the single primary action button — reuse unchanged for each candidate's own CTA). |
| Destructive | `T.negative` = `#f26d6d` (dark) / `#c6464c` (light) | Put/protective-structure manchete color, negative P&L values. the CTA button border/fill (`T.accentTint`) — nothing else. Manchete color is
always `T.positive` (call-leaning) or `T.negative` (put/collar-leaning),
never accent, matching the existing single-candidate card and the Phase 18
tira exactly.

## Interaction Decisions (the two items CONTEXT.md left open)

These were explicitly named in this agent's task prompt as genuinely open —
not pre-answered by `19-CONTEXT.md`. Documented here as **recommendations
with grounding**, not silent defaults, because this subagent has no
interactive path back to the human operator. Flagged again in the return to
the orchestrator for explicit confirmation before/during planning.

### 1. Busy/disabled treatment across sibling candidates

**Finding (traced in code, not assumed):** `PropostaDaPosicao` holds ONE
`busy` boolean for the whole position (`App.jsx:3996`), not one per candidate.
`A.abrirLastreada`/`A.abrirCollar` call `setData(s)` on success
(`App.jsx:8073,8085`), which updates `data.positions`/`data.optionPositions`
— but `useOpcoesPropostas`'s fetch effect depends only on the joined ticker
list (`App.jsx:4079`, `[chave]`), which does NOT change after an accept. **The
candidate list (`r.candidatos`) is never refetched after a successful accept**
— it stays stale in front-end state until the ticker list itself changes
(e.g. navigating away and back).

**Recommendation:**
- Reuse the SAME single per-position `busy` boolean across every candidate's
  CTA in that position — do not introduce per-candidate busy state. This
  falls out of the existing code structure for free: the moment any one
  candidate's `onClick` handler sets `busy = true`, ALL candidate CTAs in
  that position disable simultaneously via `disabled={busy || degradado}` on
  each button, because they all read the same state variable. This satisfies
  "sibling greys out on click" without new state.
- The clicked candidate's button additionally shows its own busy label if
  the existing pattern supports it (today's single-CTA pattern does not have
  a distinct "in flight" label beyond `disabled` — do not invent one; reuse
  `disabled` alone, consistent with `PropostaLastreada` today).
- **After resolve:** on success, do NOT attempt to invent a "this option is
  no longer available" inline message on the sibling. The stale sibling
  re-enables (`busy` resets to `false` in the existing `finally` block) and
  remains visually normal. If the user then taps it, the backend's existing
  `ORDER_LOCK`-guarded validation in `store.py` rejects with the existing
  `ValueError` text, surfaced via the existing flash/toast (`flash(...)`) —
  the same mechanism already in production, not a new one. This matches
  CONTEXT.md's explicit conservative stance ("não implementar uma trava nova
  onde a trava de sempre já resolve") extended to the visual layer: no new
  guard, no new copy, no new inline state.
- Do NOT build a refetch-after-accept mechanism to solve staleness — out of
  scope for this phase per CONTEXT.md (not named in Implementation Decisions
  or Claude's Discretion); flag as a possible future improvement only if the
  planner/operator decides otherwise.

### 2. Primary (put_protecao) vs. secondary (collar) visual weight

**Recommendation:** equal visual weight, order-only cue, no badge.

- Both candidate cards use the identical style object (same padding, radius,
  background, border, font sizes) as `OportunidadesOpcoes` items today — no
  size/elevation/border difference between them.
- The ONLY distinguishing cue is left-to-right order in the horizontal
  scroll row: `put_protecao` renders first (leftmost), `collar` second —
  this directly matches the ordering CONTEXT.md already locked for
  `candidatos[0]` (backward-compatibility reasoning: put_protecao first is
  both "most conservative" and "what old consumers of `.proposta` already
  see").
- Do NOT add a "recomendado" / "mais popular" / star badge on either
  candidate. CONTEXT.md frames these as genuinely competing strategies for
  the same technical read (pay for pure protection vs. finance the
  protection by giving up upside) — not a ranked primary/fallback pair.
  Badging one as "recommended" would contradict that framing and would be
  new copy/new visual weight this spec has no mandate to invent.
