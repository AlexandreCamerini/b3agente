# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note — two design systems, not one

This phase touches **two separate, architecturally independent** React codebases, each with its own hand-rolled token system (no shared import between them):

- **Surface A — Consumer app** (`web/src/App.jsx`, ~7600 lines): two-axis token system (theme dark/light × mode Estudo/Operador), Brand Book v2, guardian-tested (`web/tests/test_brand_book_v2_tokens.mjs`). Touched by **FIX-C11, FIX-C30** (partial — the admin-gated `FonteDadosScreen` lives inside this file too).
- **Surface B — Admin portal** (`web-admin/src/App.jsx`, ~1200 lines): single dark-only palette, hardcoded copy of `PALETTE.dark` + `MODE_OPERADOR.dark` (Operador gold accent fixed — ADR-012 Fase 5, `web-admin/src/App.jsx:9-13`). Touched by **FIX-C35, FIX-C36, FIX-C37, FIX-C30 (verify-only)**.

FIX-C12, FIX-C20, FIX-C31, FIX-C32 have **no UI surface** in this phase — see the "No-UI Requirements" section for the explicit scope guard against accidental UI additions. **FIX-C19 was re-scoped after a plan-checker finding** (see 03-CONTEXT.md D-02 revised) — it DOES have a UI surface now, a small status-summary card; see its own Phase-Specific Component Notes entry below, not the no-UI table.

Every new/changed string and color below cites the exact existing pattern it must match — this phase extends established components (`KillSwitchBox`, the "Orçamento brapi" `Card`, the `TechnicalModal` fonte line), it does not introduce new visual language.

> **Established Codebase Exception — `7px 0` row padding, `17px 18px` card padding, `14px` inline spacing (not 4px multiples):**

## Dependency Notes — backend fields this phase's UI assumes but does not itself wire

The planner must sequence backend plumbing before the corresponding front-end read, in both cases below (mirrors this phase's own C11→C30 sequencing note in ROADMAP.md):

1. **`source` field missing from `/api/technicals/{ticker}`** (blocks C-11). Traced live: `technical_snapshot.get()` (`server/app/technical_snapshot.py:185`) does not propagate `source` from its `loader` callback's result (`candle_provider.get_history()`, which DOES return `out["source"]` — `server/app/candle_provider.py:295-321`) into the snapshot it returns; `main.py`'s `technicals` route (`main.py:971-993`) then builds its `payload` dict without a `source` key at all. CONTEXT.md's canonical_refs states "o campo já existe na resposta da API, só não é lido corretamente no front" — **that claim is true for `/api/history` and `/api/quotes`, but false for `/api/technicals`, which is the endpoint `TechnicalModal` actually calls.** This is a real gap the planner must close (propagate `source` through `technical_snapshot.get()` into the `/api/technicals` payload), not a front-end-only fix.
2. **`degradado` flag not exposed to any front-end-reachable endpoint at the granularity C-30 needs** (blocks the Consumer-surface half of C-30). `brapi_budget.degradado("spot")` is called internally at `candle_provider.py:338` (TTL tripling) and separately re-derived inside `brapi_budget.snapshot()` (`server/app/brapi_budget.py:181`, per-fatia). The admin-portal Custos card and the consumer `FonteDadosScreen` both already consume shapes derived from `snapshot()`, so plumbing degradado through to those two is mostly a payload-shape check (verify, per Copywriting Contract above). The genuinely new plumbing is getting a `degradado`-for-`spot` boolean into `/api/technicals` (or `/api/quotes`) so the **regular end-user** sees it on the same line as the source label — this endpoint has no budget-state field today and needs one added.
