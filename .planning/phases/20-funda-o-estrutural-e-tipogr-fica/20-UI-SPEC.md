# Phase 20 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** this is the "fundação" phase of v1.5 — it touches the shell,
`GlobalStyle()`, and shared tokens (`MONO`/`DISPLAY`, three new numeric-scale
constants), not screen content. It introduces **zero** new visual language:
every value below is either a literal already shipped in production
(`T.*`, `MONO`, `DISPLAY`, the `720px` in `BottomNav`) or a value locked in
`20-CONTEXT.md` from the approved design session
(`bencium-controlled-ux-designer`). This spec documents exact call sites so
planner/executor implement against real line numbers, not paraphrases.

**Scope conflict surfaced (not resolved silently):** `ROADMAP.md` Phase 20
success criterion #4 reads *"todo valor financeiro na tela usa um dos três
tamanhos nomeados... nunca um tamanho solto"* — read literally, this implies
Histórico/Watchlist/Portfólio must already show migrated numbers by the end
of Phase 20. `20-CONTEXT.md`'s "Escopo desta fase" explicitly narrows this:
*"nenhum número de tela específica migra à força aqui... esta fase entrega a
fundação, não a migração de todo o app"* — screen-by-screen migration is
Phase 21/22's job. Per this agent's mandate (CONTEXT.md decisions govern,
not re-litigated), **this spec follows CONTEXT.md's narrower scope**. Two
sub-parts of ROADMAP's criterion #4 resolve differently under that scope,
and the difference matters for what "done" means:
- **TYPO-01 (tabular-nums, digit alignment) IS fully satisfied by Phase 20
  alone**, with zero screen migration needed — `tabular-nums` goes into the
  shared `MONO` constant (`App.jsx:236`), and `MONO` is already referenced
  ~155 times across the file. Every existing money/quantity value that
  already uses `fontFamily: MONO` gets aligned digits for free the moment
  this one constant changes.
- **TYPO-02 (named size scale `numHero`/`numBody`/`numMicro`) is NOT fully
  satisfied by Phase 20** — the constants are defined and exported for
  reuse, but no existing screen's inline `fontSize` literal is migrated to
  them in this phase (CONTEXT.md is explicit that this is Phase 21/22's
  job, screen by screen). Flag this explicitly to `gsd-ui-checker` and the
  orchestrator: ROADMAP's literal wording for criterion #4 is only fully
  true after Phase 21/22 complete, not at the end of Phase 20.

## Typography

### Numeric scale (TYPO-01, TYPO-02)

Three new style-object constants, declared as plain JS objects (spread via
`style={{...numHero, ...}}`, matching the file's existing pattern — NOT
CSS classes), placed adjacent to `MONO`/`DISPLAY` (`App.jsx:236-243`):

| Constant | fontSize | fontWeight | Usage (per CONTEXT.md, applied where THIS phase touches a number) |
|----------|----------|------------|----------|
| `numHero` | 34px | 700 | Hero-scale financial value (e.g. a screen's single headline number). No existing call site is migrated to this by Phase 20 — defined for Phase 21/22 to consume when they touch Histórico/Watchlist/Portfólio. |
| `numBody` | 18px | 700 | Body-scale financial value — closest existing match is `Topbar`'s patrimônio value (`App.jsx:833`, currently `fontWeight:700, fontSize:"18px"` inline, already the exact numbers this constant encodes). Migrating that one call site to `{...numBody}` is in-scope and low-risk since the values are byte-identical to what's already there — recommended but not mandated by CONTEXT.md; if the planner chooses to apply it, this is the one safe, zero-visual-diff call site. |
| `numMicro` | 13px | 600 | Micro-scale financial value (list rows, secondary numbers). No existing call site migrated by Phase 20. |

All three MUST be plain JS style objects, e.g.:
```js

const numBody  = { fontSize: "18px", fontWeight: 700 };
const numMicro = { fontSize: "13px", fontWeight: 600 };
```
Naming: `numHero`/`numBody`/`numMicro` are the names already used in the
approved design session (`20-CONTEXT.md`, Claude's Discretion). Keep unless
they collide with an existing identifier in `App.jsx` (none found by this
research pass — grep confirmed no existing `numHero`/`numBody`/`numMicro`
symbols).

### tabular-nums (TYPO-01)

Add `font-variant-numeric: tabular-nums` directly to the `MONO` constant
(`App.jsx:236`):
```js
const MONO = "ui-monospace,'SF Mono',Menlo,Consolas,monospace";
```
`font-variant-numeric` is not a font-family value — it cannot be concatenated
into the `MONO` string itself. Per CONTEXT.md's intent ("entra direto no
stack MONO existente... afeta todo uso de MONO de uma vez"), the correct
mechanical implementation is a CSS rule in `GlobalStyle()` targeting every
element that sets `font-family` to the `MONO` stack, OR (simpler, matches
"sem precisar tocar em cada call site" intent) a single attribute selector
rule added to `GlobalStyle()`'s CSS template string:
```css
.b3 [style*="ui-monospace"]{ font-variant-numeric: tabular-nums; }
```
This is fragile (attribute-selector-on-inline-style is unusual). The
**more robust option**, and the one this spec recommends the executor
verify against the codebase's actual rendering pattern: since every mono
value already goes through `style={{ fontFamily: MONO, ... }}`, and React
inline styles cannot be globally patched via a shared string without a
wrapper, the cleanest fix consistent with "one constant, no per-call-site
edit" is to make `MONO` a **style-object partial** instead of a bare
string, e.g.:
```js
const MONO = "ui-monospace,'SF Mono',Menlo,Consolas,monospace"; // keep for
  // any call site that reads MONO as a bare font-family string
const MONO_NUM = { fontFamily: MONO, fontVariantNumeric: "tabular-nums" };
```
...but this DOES require touching call sites (spread `{...MONO_NUM}`
instead of `fontFamily: MONO`), contradicting CONTEXT.md's stated
intent of a zero-call-site-edit change. **Flag to planner:** CONTEXT.md's
plan ("entra direto no stack MONO existente... afeta todo uso de MONO de
uma vez, sem precisar tocar em cada call site individualmente") is
technically not achievable with `fontFamily: MONO` as a bare string
constant, since `font-variant-numeric` is a separate CSS property, not part
of a font-family value. The GlobalStyle CSS-selector approach
(`[style*="ui-monospace"]`) is the only way to satisfy "zero call site
edits" literally; the planner must pick one of these two paths explicitly
during `/gsd-plan-phase 20` — this is a genuine implementation ambiguity
CONTEXT.md did not resolve at the mechanical level, not a design decision
this spec can silently make.

## Motion Contract (MOTION-03)

### New rule (CONTEXT.md-specified)

Add to `GlobalStyle()`'s CSS template string:
```css
@media (prefers-reduced-motion: reduce) {
  .b3 *, .b3 *::before, .b3 *::after {
    transition-duration: 0.01ms !important;
    animation-duration: 0.01ms !important;
  }
}
```

### Interaction with the existing narrow rule — decided, not left ambiguous

`GlobalStyle()` already has, at `App.jsx:323`, INSIDE its own
`@media (prefers-reduced-motion: reduce)` block:
```css
.b3 .tt-track,.b3 .spin{ animation:none !important; }
```
This rule is scoped to exactly two infinite-iteration animations: the
ticker marquee (`b3tt 52s linear infinite`, `.tt-track`, `App.jsx:322`) and
the loading spinner (`b3spin .8s linear infinite`, `.spin`, `App.jsx:317`).

**Decision: KEEP the narrow rule; do not delete it, do not treat the new
broad rule as a replacement.** Rationale: `animation-duration: 0.01ms`
does NOT stop an `infinite`-iteration animation — it makes it complete a
full cycle every 0.01ms and repeat forever, which for a spinner or a
52-second marquee traveling -50% of its width produces a very fast
flicker/strobe, not a frozen state. That is the opposite of what
"prefers-reduced-motion: reduce" exists for (vestibular-safety), and is a
known limitation of the "shrink duration to near-zero" pattern for
`infinite` animations specifically. `animation: none` is the only way to
fully stop these two. Both rules coexist safely: the broad rule handles
every transition and every future non-infinite animation (Phase 22/23's
future additions) with zero extra code; the narrow rule remains the
correct, minimal fix for the two infinite-loop animations that predate
this phase. **Source-order requirement:** the new broad-rule media query
block must be placed textually AFTER line 323's block (or the two must be
merged into one `@media` block with the narrow rule's more specific
selector listed after the broad one) so the cascade resolves in favor of
`animation:none` for `.spin`/`.tt-track` specifically — both rules carry
`!important`, so whichever is later in source order wins on the tied
selectors under equal specificity. The current insertion point implied by
CONTEXT.md (near the top of `GlobalStyle`, per "cobre a transição de
tema/modo já existente") is compatible with this as long as the executor
does not accidentally place the new block textually below line 323 in a
way that would flip precedence unfavorably — verify final source order
after edit, don't assume.

### Mode-switch transition (`App.jsx:311-312`)

```css
.b3-mode-switch, .b3-mode-switch *{ transition: background-color .35s ease, color .35s ease, border-color .35s ease, fill .35s ease !important; }
```
This unconditional (`!important`, no media query) rule is exactly the kind
of case MOTION-03 exists to gate. The new broad rule, if placed after this
one in source order (which line 323's existing block already is, relative
to line 312), correctly overrides it to `0.01ms` under reduced motion —
verify this ordering holds after edit; it is the entire mechanism by which
MOTION-03's "mode-switch transition already existente" gets covered, per
CONTEXT.md's own stated intent.

## Structural Contract (FIX-01, FIX-02, SYS-04)

### FIX-01 — horizontal overflow containment

Add `overflow-x: hidden` to the `.b3-shell` CSS rule inside `GlobalStyle()`
(`App.jsx:290`, currently `.b3-shell{ height:100vh; height:100dvh; }`) →
becomes `.b3-shell{ height:100vh; height:100dvh; overflow-x:hidden; }`.

Note for the executor: the shell's inline `style` object (`App.jsx:8920`)
already sets `overflow: "hidden"` (both axes) on the same element — the
live audit measured `scrollWidth` 504px vs `clientWidth` 375px anyway,
meaning that inline rule alone does not close the defect (likely because a
flex descendant without `min-width:0` forces intrinsic width upstream of
where `overflow:hidden` clips). Adding the CSS-class rule is
belt-and-suspenders per CONTEXT.md's explicit reasoning ("a causa raiz
medida... é contenção ausente na raiz") — do not treat the existing inline
`overflow:hidden` as already sufficient; the audit evidence says it is not.

### FIX-02 — MarketStatusBadge truncation

Add `minWidth: 0` (or CSS `min-width: 0`) to the flex-container parent of
`MarketStatusBadge` at BOTH call sites:
1. `Topbar` (`App.jsx:827`, the wrapping `<div style={{ marginTop: "4px", minWidth: 0 }}>` — **note: this exact div already has `minWidth: 0`** as of the current read. Re-verify at execution time whether the ACTUAL missing `min-width:0` is one level up, on the flex row at `App.jsx:802` (`display:"flex", ... marginRight:"auto", minWidth:0` — also already present) or `App.jsx:804` (`display:"flex", alignItems:"center", gap:"7px", minWidth:0` — also present). **This spec's code read did not find a Topbar container missing `min-width:0`** on the direct ancestor chain of `MarketStatusBadge` — flag this to the planner: either the defect is on a different ancestor not yet identified (e.g. the outer `Topbar` flex row itself, `App.jsx:795`, which has `display:"flex", alignItems:"center", gap:"12px"` with NO `minWidth:0`), or the truncation defect is already partially mitigated and needs re-measurement before writing the plan. Do not assume `App.jsx:795` is the fix without confirming — measure `scrollWidth` on the badge's `<span>` under a long "Mercado fechado, abre..." string in a live/dev check.
2. Home (`App.jsx:1871`, `<div style={{ marginTop: "4px" }}>` — **this one genuinely lacks `minWidth: 0`**, confirmed by direct read. Add it here: `<div style={{ marginTop: "4px", minWidth: 0 }}>`.

`MarketStatusBadge` itself already declares `textOverflow:"ellipsis"`,
`overflow:"hidden"`, `whiteSpace:"nowrap"`, `minWidth:0` on its own label
`<span>` (`App.jsx:783`) — no change needed inside the component; the fix
is entirely in ancestor containers per CONTEXT.md.

### SYS-04 — desktop content width cap

Replace the `maxWidth: "1060px"` literal at `App.jsx:8967` with the new
`720px` constant (see Spacing Scale above), matching `BottomNav`'s existing

constant, not two independent literals, to prevent future drift.
