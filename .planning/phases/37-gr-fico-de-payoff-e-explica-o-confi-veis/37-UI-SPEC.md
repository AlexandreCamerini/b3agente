# Phase 37 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase boundary reminder (`37-CONTEXT.md` `<domain>`):** this phase extends
`PayoffChart.jsx` (SVG, already in production, 3 real consumers per D-08) to
consume `dominio_da_curva()`/`segmentos_da_curva()` (Fase 36) and adds a new
deterministic explanation-text layer. It is renderização + apresentação —
never a new financial calculation on the front (princípio 5, `CLAUDE.md`).
No RESEARCH.md exists (skipped); the exact backend route/field names that
carry `dominio`/`segmentos`/`valor_hoje` to the front are **not yet wired**
(confirmed by grep: zero call sites reference `dominio_da_curva`/
`segmentos_da_curva` outside `opcoes_payoff.py` itself). Where this document
proposes a field/prop name for data that doesn't exist yet, it is flagged
explicitly as **proposed, not confirmed** — the planner/research step still
owns picking the actual wire path; this UI-SPEC owns what renders once the
data arrives.

## Layout & Interaction Contract

**Visual hierarchy (primary focal point):** the P&L curve (color-coded
`corLucro`/`corPerda`) remains the card's primary visual anchor, unchanged
by this phase. The new axis labels/marks (zero line, Y-axis ticks, strike/
spot marks) are secondary — they annotate the curve, never compete with it
for attention (hence muted/faint tokens, never accent). The explanation
text block (§3) is tertiary — it sits below the chart and restates in words
what the curve already shows visually.

This is the load-bearing section: `37-CONTEXT.md` locks *what* must appear
(CHART-01..05, EXPL-01..03) but explicitly leaves *where/how* to the UI
phase ("Nome exato do campo novo... Claude's Discretion", "Onde exatamente a
função pura de explicação mora... Claude's Discretion", "Tratamento visual
exato do estado de erro/indisponível... decisão de quem planejar/executar").
This document resolves those.

### 0. New props `PayoffChart` needs (prop-level contract, not backend wiring)

`PayoffChart({ estrutura, emReais, cp, palette })` today. This phase adds
three optional props, each independently nullable so the 3 consumers can
adopt them incrementally without breaking each other:

| Prop | Shape (proposed, camelCase — mirrors backend `snake_case` 1:1, zero arithmetic, same discipline as `estruturaParaPayoff.js`'s existing guardian) | Source |
|------|-------|--------|
| `dominio` | `{ xMin, xMax, yMin, yMax, margem, spot, ganhoIlimitado, perdaIlimitada, motivo }` — any field may be `null` | `dominio_da_curva(perfil, spot)`, Fase 36. Note: the function's own signature already takes `spot` as input and echoes it back in its return dict (`opcoes_payoff.py`, `dominio_da_curva`, `"spot": round(spot_num, 4)...`) — there is **no separate spot prop**; `PayoffChart` reads the X-axis spot mark (CHART-02, §1.3) from `dominio.spot`, not from a standalone field. Collapsing this into one round-trip avoids inventing a second copy of the same number. |
| `segmentos` | `[{ de, ate, inclinacao: "positiva"\|"negativa"\|"zero", ePlato }]` | `segmentos_da_curva()`, Fase 36 |
| `valorHoje` | `{ carregando, erro, dados: { porAcao, emReais } } \| null \| undefined` | New MCP fetch, CHART-05/D-01/D-02 |

**Fallback rule (preserves today's 3 consumers unmodified where data isn't
wired yet):** when `dominio`'s `xMin`/`xMax`/`yMin`/`yMax` are all
non-`null`, `PayoffChart` uses them for `sx()`/`sy()`. Otherwise it falls
back to **today's existing local `useMemo` domain calculation**, unchanged —
this is what keeps `CuradoriaEstruturas.jsx`'s `payoffPrimeiro` block (D-09:
gets the corrected chart automatically, no extra work) and any call site
that hasn't been updated to pass `dominio` yet from breaking.

**Open gap, flagged not solved by this document:** the real unresolved
question is not "does `PayoffChart` need a new prop for spot" (it doesn't —
see the `dominio.spot` note above) but **does whichever backend code calls
`dominio_da_curva(perfil, spot)` actually have a live spot value to pass
in.** Verified by grep: zero call sites invoke `dominio_da_curva`/
`segmentos_da_curva` today outside `opcoes_payoff.py` itself, and zero call
sites in `SecaoAnalisar.jsx`/`SecaoComparar.jsx`/`CuradoriaEstruturas.jsx`/
`estruturaParaPayoff.js` reference a spot/cotação value at all. Two
candidate sources for the planner to pick between when wiring the route:
(a) the same live quote CHART-05's `get_option_chain` fetch will compute for
mark-to-market — if so, `dominio.spot` (and therefore the X-axis spot mark)
is only populated where that fetch succeeds, same gating as the "hoje"
block (§2); or (b) a cheaper already-fetched quote elsewhere in the
workspace (none found in this research pass — the planner should re-check
once the actual route is chosen). **This UI-SPEC's visual contract for the
spot mark (§1.3) applies either way**; only the *availability* of
`dominio.spot` differs. `dominio.spot === null` → the mark simply does not
render (same optional-field pattern already used throughout this file,
e.g. `emReais` today, `PayoffChart.jsx:185`).

### 1. SVG Geometry Contract — the 320×192 viewBox

This is a graphics coordinate system, not a page-margin grid: its existing
constants (`PAD_T=18`, `FONTE_MIN=11.5`, the `44`/`52`/`28`/`5`/`8` pixel
collision thresholds already in `PayoffChart.jsx`) are **not** multiples of
4 and were never meant to be — they are tuned for legibility inside a fixed
320×192 viewBox (`PayoffChart.jsx:35-49`, Fase 31 D-07). New values in this
section follow the same category: declared and justified by the same
legibility-floor math the file already uses, not the DOM-level 8-point scale
(that scale governs §4 below — the new Kicker/block spacing around the SVG,
which IS ordinary CSS).

**`W=320`/`H=192` do not change** — the file's own comment locks this to the
card's aspect ratio at 375px (`PayoffChart.jsx:38-39`); this phase respects
that boundary.

#### 1.1 — CHART-01: zero line label "R$ 0" + Y-axis scale

Today: dashed zero line exists (`PayoffChart.jsx:268-269`), unlabeled; no Y
tick labels anywhere. Contract:

- **Y-axis tick labels use the file's existing `fmt()` (2 decimals, comma),
  never integers.** Per-share option results in this product are routinely
  sub-R$1 — the phase's own golden reference case (trava de alta, strikes
  49,17/49,67, lote 100) has ganho/perda máx R$ 25,00 **for the lot**; per
  share that is R$ 25,00 ÷ 100 = R$ 0,25, and `y_max = 0.25 × 1.15 ≈ 0.29`.
  Rounded to an integer that reads `"0"` — for the exact structure this
  phase treats as canonical, an integer scale would show "0" at the top,
  zero line, and bottom alike: the "no visible scale" failure CHART-01
  exists to fix. 2-decimal precision is not optional here.
- **`PAD_E` grows from `10` to `48`.** Budget, recomputed for 2-decimal
  labels: worst case is `"-99,99"` (6 chars: minus, 2 digits, comma, 2
  digits). At `FONTE_MIN=11.5px`, ≈`0.58×11.5≈6.7px`/char → `6×6.7≈40px` +
  4px tick mark + 4px breathing margin ≈ `48px`. This is the single most
  consequential geometry change in this phase — flagged explicitly, not
  buried: it shifts the curve's left edge inward by 38px (≈12% of `W`),
  same category of tradeoff the file already made once (Fase 31 D-07 grew
  `H`/`PAD_T`/`PAD_B` for legibility over raw plot area).
- **3 Y-axis ticks**, left column, `x = PAD_E - 4 = 44`, `textAnchor="end"`,
  `dominantBaseline="central"` (avoids manual vertical-offset math), a 4px
  horizontal tick mark from `x=44` to `x=PAD_E=48`, `fontSize={FONTE_MIN}`,
  `fill={T.textMuted}` (existing token):
  - top: `sy(yMax)` when `dominio.yMax` is non-null, label = `fmt(yMax)`, no
    unit prefix (unit stated once in the caption below, §1.4). If
    `dominio.ganhoIlimitado`, **omit this tick** — the existing ↑ arrow
    (CHART-03, already implemented) is the honest signal there; inventing a
    numeric ceiling where the service declared none would be exactly the
    "platô falso" CHART-03 forbids.
  - zero: `yZero` (existing), label = `cp.opcoesEixoZeroRotulo` default
    `"R$ 0"` — **exact literal from CHART-01's own wording**, only the key
    name is discretion.
  - bottom: `sy(yMin)` when `dominio.yMin` is non-null, label = `fmt(yMin)`.
    Omit if `dominio.perdaIlimitada` (same reasoning as top).
  - **Dedup rule:** if the top or bottom tick's `y` lands within 3px of
    `yZero` (i.e. the extreme value IS zero — a structure whose max gain or
    max loss is exactly 0), suppress that extreme tick and show only
    `"R$ 0"`. Two overlapping labels at the same row is a worse failure mode
    than one omitted redundant number.
- **Existing breakeven/strike anchor threshold updates**: today's
  `x < 28 ? "start" : ...` (`PayoffChart.jsx:291`) is now unreachable on the
  left (nothing renders below `x=48`) — change the threshold to
  `x < PAD_E + 18 ? "start" : ...`, preserving the same ~18px near-edge
  margin logic, just anchored to the new `PAD_E`.

#### 1.2 — CHART-02: strikes marked and rotulados (new), reusing the existing breakeven collision algorithm

`37-CONTEXT.md`'s own "Reusable Assets" note says reuse the same
collision-suppression algorithm for strikes, not invent a second one — this
contract does exactly that by **merging strikes into the same sorted,
44px-gap collision pass** that breakevens already run
(`PayoffChart.jsx:284-301`), differentiated by **line style and color**,
never by adding a second label row (checked: a second row at
`H-PAD_B+16..+27` would clip against `H=192`, see arithmetic below —
merging into one row is required, not just tidier):

| Mark | Line | Color | Label row (shared, `H-PAD_B+12`) | Priority when two marks compete for the same 44px slot |
|------|------|-------|-------|-------|
| Breakeven (existing) | full height `PAD_T→H-PAD_B`, dashed `"2 4"` | `T.textMuted` | numeric, `fmt()` | **wins** — pre-existing "must-show" fact (CHART-02 doesn't ask us to evict it) |
| Strike (new) | full height `PAD_T→H-PAD_B`, dotted `"1 3"` (denser than breakeven's dash, visually ranks below it) | `T.borderFaint` (existing token, lighter than `T.textMuted`) | numeric, `fmt()` | loses to breakeven; wins over nothing else in this row |

Both participate in ONE sorted-by-`sx()` array before the 44px gap check
runs, so a strike and a breakeven at nearly the same price never print two
overlapping numbers — only the breakeven's number prints, the strike's
dotted line still draws (line is always drawn, per the file's own existing
philosophy at `PayoffChart.jsx:281-283`: "a LINHA... é SEMPRE desenhada —
é dado, não decoração — só o TEXTO se suprime").

Row-clip check that rules out a second label row: `H-PAD_B+12 = 192-32+12
= 172`; a second row at `+11` line-height would need `183`, and
`183+11.5(font)≈194.5 > H=192` — clips. Confirms the merge-not-stack design
above is required, not optional.

Accessibility: append strike values to the existing `descricao`/`<title>`
sentence (`PayoffChart.jsx:231-242`) — that string is already hardcoded PT
text, not routed through `cp` (existing, unremarked inconsistency in this
file); new additions match that same pattern rather than introducing a new
one. Example: `"Strikes desta estrutura: " + strikes.map(fmt).join(", ") + "."`.

#### 1.3 — CHART-02: spot marked "hoje {preço}" (new), reusing the existing `cenarios` top-anchored collision algorithm

Reads `dominio.spot` (see §0 — not a standalone prop). Spot gets a
**visually distinct family** from strike/breakeven — solid line (not
dashed/dotted) + a filled circle at the top, reusing the exact marker
already drawn for `cenarios` (`PayoffChart.jsx:303-328`: `<circle r="3"
fill={T.textPrimary}/>` + text near the top, with its own 52×14 collision
check). Spot joins that SAME top collision list (not a third algorithm):

- Line: full height `PAD_T→H-PAD_B`, solid, `stroke={T.textPrimary}`
  (existing token — already the `cenarios` dot's fill color, so spot reads
  as "part of the same marker family, ranked highest" for free).
- Dot: `<circle r="3" fill={T.textPrimary}/>` at `(sx(dominio.spot),
  sy(spotResult))` if a result value at that price is computable, else at
  `yZero`.
- Label: `(cp.opcoesHojePrefixoEixo || "hoje") + " " + fmt(dominio.spot)` —
  **no currency prefix**, matching the file's own D-24.2 rule that this axis
  is PRICE, never money (`PayoffChart.jsx:15,193-194`).
- **Priority in the top collision list: spot wins over a colliding
  cenário.** CHART-02 requires spot "sempre marcado" (unconditional);
  `cenarios` are optional secondary annotations from the service that
  already tolerate suppression today (`PayoffChart.jsx:312-314`, `colide`
  check) — extending that same tolerance to yield to spot is the smaller
  behavior change, not a new rule.
- `dominio.spot === null` (no live quote reached domain calc) → mark absent
  entirely, no placeholder/degraded state drawn.

#### 1.4 — CHART-01: "multiplique pelo lote" legend

Append to the existing caption line below the SVG
(`PayoffChart.jsx:340-345`, unchanged position/style — `fontSize: 11px`,
`T.textMuted`): after `"Eixo vertical: resultado " + opcoesPorAcaoRotulo +
"."`, add one sentence, new key `cp.opcoesEixoVerticalLoteAjuda`, default
`"Multiplique pelo lote para o valor total."` This satisfies CHART-01's
"legenda 'multiplique por lotSize para o lote'" requirement **as caption
text below the SVG**, not crammed into the 48px-wide Y-axis column —
consistent with this file's existing division of labor (SVG shows shape,
caption states units/precision in words).

#### 1.5 — CHART-03: in-chart "sem teto"/"sem piso" label next to the arrow (closes a real gap)

Today the ↑/↓ arrows (`PayoffChart.jsx:332-337`) are `aria-hidden` with no
visible in-chart text — "sem teto"/"sem piso" only appears in the caption
paragraph below. CHART-03's literal wording ("seta... rotulada") asks for
the label attached to the arrow itself. Contract: a short text label
immediately left of each arrow, same row, `textAnchor="end"`, `x = (arrow
x) - 16`, `fontSize={FONTE_MIN}`, color matching that side (`corLucro`/
`corPerda`, existing).

- Gain side: reuse `cp.opcoesGanhoIlimitado` verbatim (`"sem teto"`, already
  short — no new key).
- Loss side: the existing `cp.opcoesPerdaIlimitada` is long (`"sem piso
  declarado pelo serviço"`, 6 words) — does not fit this corner. **New key**
  `cp.opcoesPerdaIlimitadaCurta`, default `"sem piso"` — short form for
  in-chart use only; the long form keeps its existing job in the
  caption/cabecalho text where there is room to state the nuance.

Residual risk, named and accepted rather than solved exhaustively (matches
this file's own stated philosophy of graceful degradation over a perfect
layout solver): if a strike/breakeven label also lands in that exact corner,
the existing bottom collision pass (§1.2) already suppresses the
lower-priority text — visual crowding in that specific corner is bounded,
not eliminated.

### 2. CHART-05 — "hoje · valor de mercado" block, separate from "no vencimento"

**Root of the confirmed production bug:** today's `cabecalho` top line
(`PayoffChart.jsx:178-180`) reads only `{nome}{" · " + vencimento}` — nothing
on screen currently frames this whole card as a *"no vencimento"* figure.
CHART-05 requires both framings to be visible and distinct. This reuses the
exact regulatory pattern this product already established for "two valid
numbers, neither more true than the other" — the Fase 32 D-05 frase-ponte
("nenhuma é mais certa que a outra"), same neutrality principle, same
solution shape: **two parallel `Kicker`s of equal visual weight**, not a
primary/secondary hierarchy.

```
caixa (existing bordered card, unchanged: T.bgPanel, 12px radius, 12px padding)
  Kicker: cp.opcoesNoVencimentoTitulo → "No vencimento" + " · " + vencimento   [NEW label, existing Kicker import from uiOpcoes.jsx]
  {nome}                                                                       [existing line, unchanged]
  por-ação block (custo/ganho/perda)                                          [existing, unchanged]
  em-reais block                                                              [existing, unchanged]
  breakeven block + ajuda                                                     [existing, unchanged]
  ── (only when `valorHoje` prop is not null/undefined — see below) ──
  Kicker: cp.opcoesHojeTitulo → "Hoje · valor de mercado"                     [NEW]
  valorHoje.carregando → muted line, cp.opcoesHojeCarregando                  [NEW]
  valorHoje.erro       → <ErroDoMcp erro={valorHoje.erro} cp={cp}/>            [reuse, D-01/D-02 canonical_refs]
  valorHoje.dados      → same 2-line "por ação" / "em reais" pattern as above,
                          using proposed fields valorHoje.dados.porAcao /
                          valorHoje.dados.emReais (NOT CONFIRMED — backend
                          route not wired yet, see §0)
  Kicker ajuda: cp.opcoesHojeAjuda → "Preço de mercado agora — pode mudar a
                          qualquer momento, diferente do resultado no
                          vencimento acima."
```

**`valorHoje` absent entirely (`null`/`undefined`) vs. present-but-failed are
different states, rendered differently** — mirrors the existing optional-prop
pattern (`emReais ? (...) : null`, `PayoffChart.jsx:185`): when the caller
(D-02: `SecaoComparar.jsx` for every candidate except the 1st in ranking
order) never attempted the fetch, the whole "Hoje" Kicker+block is **absent**
— not a degraded/error state, just not applicable here. Only when a fetch
WAS attempted does the block render (loading, error, or data). This is a
caller-level decision (`SecaoComparar.jsx`/`SecaoAnalisar.jsx` decide
whether to pass `valorHoje` at all), not something `PayoffChart` infers.

**Nested-box acceptance note:** `ErroDoMcp`'s `Aviso` renders its own
border+radius+padding, so an error state here is a bordered box inside
`cabecalho`'s already-bordered box. This is explicit reuse per
`37-CONTEXT.md`'s canonical_refs ("reusar `ErroDoMcp`/`Aviso` já
existentes"), not a new visual invented by this document — accepted as-is,
not a new risk requiring separate sign-off.

### 3. EXPL-01/02/03 — explanation block (new component)

**Home:** a new component (proposed name `ExplicacaoPayoff`, file location
Claude's Discretion per `37-CONTEXT.md` — `uiOpcoes.jsx` if it ends up

<PayoffChart .../>
<RazaoGanhoPerda razao={razao} cp={cp} />
<ExplicacaoPayoff segmentos={segmentos} spot={dominio && dominio.spot} razao={razao} cp={cp} />   ← NEW, same 10px gap

**Content structure (D-06/D-07):** one sentence per segment, `\n`-separated
(the `Aviso` component already sets `whiteSpace: "pre-wrap"`, so newlines
render as visible line breaks — no new CSS needed). Order: **the segment
containing `spot` first**, then the remaining segments in their original
left-to-right array order (skip the spot one on the second pass — literal
reading of D-07, not just "where am I now").

**Sentence templates (concrete defaults — exact wording refinable at
plan/execute time within these constraints: name inclinação/platô/direção
in plain PT, never the EXPL-02 banned vocabulary, reuse `razao` literally
if the ratio is mentioned, spot segment always first):**

| Case | Template |
|------|----------|
| Spot's segment, `inclinacao: "positiva"` | `"Hoje, com o ativo em R$ {spot}, você está numa faixa de alta: se o preço subir, seu resultado melhora; se cair, piora."` |

| Spot in the tail, `perdaIlimitada` | `"Hoje, com o ativo em R$ {spot}, você está na faixa sem piso de perda: quanto mais o preço subir, maior a perda, sem limite declarado pelo serviço."` |

| Other finite segment, `"negativa"` | `"Entre R$ {de} e R$ {ate}, o resultado cai conforme o preço do ativo sobe."` |
| Other finite segment, `ePlato: true` | `"Entre R$ {de} e R$ {ate}, o resultado fica travado — não muda com o preço."` |

**Razão G/P closing line (optional, EXPL-03 guardrail):** if the composed

planner extracts once, e.g. `formatarRazao(razao)` exported from
`uiOpcoes.jsx` and called by BOTH `RazaoGanhoPerda` and `ExplicacaoPayoff` —
this forecloses the exact class of bug D-05/EXPL-03 names (two independent
formatters of the "same" number drifting apart). Do not format `razao`
inline a second time inside `ExplicacaoPayoff`; import and call the same
function `RazaoGanhoPerda` already uses.

**Accessibility:** the explanation text is plain-language prose already —
no additional `aria-label` needed; it is regular DOM text, not SVG.

This phase reuses the app's established, previously-approved values; it
