# Phase 13 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

(`web/src/App.jsx`), sem tela nova, sem componente visual novo. Este contrato
formaliza decisões já travadas em `13-CONTEXT.md` (D-01..D-05, mockup

reabre nenhuma delas.

## Typography

Tratamento travado pelo `typography-specialist` (ver `13-CONTEXT.md` e bloco
`pre_resolved_design_input` do orquestrador) — aplicar EXATAMENTE assim nos
3 pontos de exibição.

| Role | Size | Weight | Line Height | Onde |
|------|------|--------|-------------|------|
| Body (prosa ao redor) | herda do elemento pai (13px subtítulo watchlist, 12.5px CatalogModal, 13px Atividade da IA) | herda (400/normal) | herda (1.5–1.55) | texto da frase inteira — NÃO recebe `MONO`, fica em `SANS`/herdado |
| Fragmento numérico "X/Y" (estado normal) | herda o tamanho do texto ao redor (não aumenta) | **700** | herda | `<span>` único ao redor só dos dígitos, `fontFamily: MONO`, `color` = mesma cor do texto ao redor (`T.textMuted`/`T.textFaint`) |
| Fragmento numérico "X/Y" (quase no limite, `usado/limite >= 0.9`) | idem | **700** | herda | mesmo `<span>`, troca só `color` para `T.warn` |
| Fragmento numérico "X/Y" (no limite, `usado === limite`) | idem | **800** (opcional, para reforço) | herda | mesmo `<span>`, `color: T.warn` — **nunca** `T.negative`/`T.positive` |

Regras obrigatórias:
- `fontFamily: MONO` aplica-se **só** ao fragmento numérico (`<span>`
  isolado), nunca à frase inteira — evitar importar o registro visual do
  painel de debug/admin para uma tela de usuário leigo (princípio "linguagem
  clara", `CLAUDE.md`).
- Dígitos tabulares (`MONO`) evitam reflow de layout quando a contagem muda
  (7/10 → 8/10 não desloca o texto ao redor).
- Threshold "quase no limite" fica a critério do planner/executor dentro da
  faixa `>= 0.9` (ex.: 9/10, 28/30) — CONTEXT.md deixou explícito como
  discricionário; este valor é o piso recomendado pelos specialists, não
  renegociável para baixo sem motivo.

⚠️ **Ação pendente antes de fechar a fase:** contraste de `T.warn` (`#fbbf24`
escuro / `#a16207` claro) em 10.5–13px contra `T.bgBase` **não foi
renderizado/medido** pelos specialists (revisão só de código-fonte). O
executor deve abrir o dev server, forçar o estado "quase no limite"/"no
limite" nos 3 pontos, e conferir legibilidade visual no tema claro
especificamente (`#a16207` é o caso de maior risco de contraste baixo) antes
de marcar a fase como pronta.

## Color

Nenhuma cor nova. Reaproveita tokens já existentes de `T` (tema ativo,
`App.jsx:69-167`).

| Role | Value | Usage nesta fase |
|------|-------|-------------------|
| Dominante (60%) | `T.bgBase`/`T.bgPanel` (existente) | fundo dos 3 containers — inalterado |
| Secundário (30%) | `T.textMuted` / `T.textFaint` (existente) | cor do texto ao redor E do fragmento "X/Y" em estado normal |
| Acento (10%) | `T.warn` (`#fbbf24` escuro / `#a16207` claro) — **não é o accent de marca** (`T.accent`) | reservado exclusivamente ao fragmento "X/Y" quando `usado/limite >= 0.9` (quase no limite) ou `usado === limite` (no limite) |
| Destrutivo | `T.negative` (mapeia `BRAND.red`) | **não usado nesta fase** — ver nota abaixo |

Accent reserved for: **apenas** o fragmento numérico "X/Y" nos 3 pontos de
exibição, e apenas nos estados quase-no-limite/no-limite. Nenhum outro
elemento desta fase ganha `T.warn`.

Nota de guardrail (travada pelo typography-specialist, não renegociável):
`T.positive`/`T.negative` (`BRAND.green`/`BRAND.red`) são reservados a P&L
(lucro/prejuízo) por convenção do projeto — reutilizá-los para "perto do
limite" faria o número de contagem parecer um resultado financeiro num app
de simulação de trading. `T.warn` é o token correto porque já é o "token de
atenção" estabelecido (`candles.alerta`, `orc.fatias.spot.degradado`), não
uma cor nova.

## Estados (todos os 3 pontos de exibição)

Cada um dos 3 locais tem 5 estados possíveis. Especificação exata por local
na seção "Copywriting Contract" abaixo; esta tabela define o CONTRATO de
estado, comum aos 3.

| Estado | Condição | Tratamento visual |
|--------|----------|---------------------|
| Normal | `count`/`used` < 90% do limite, plano tem limite (`limit != null`) | fragmento "X/Y" em `MONO` 700, cor herdada (`T.textMuted`/`T.textFaint`) |
| Quase no limite | `count`/`used` ≥ 90% do limite | fragmento "X/Y" em `MONO` 700, `color: T.warn` |
| No limite | `count === limit` / `used === limit` | fragmento "X/Y" em `MONO` 800, `color: T.warn` |
| Plano sem limite (Pro) | `limit == null` | **fragmento inteiro omitido** — nem "X/∞", nem "ilimitado" (D-03, critério de sucesso 5: "sem número fabricado"). A frase ao redor permanece, só sem o segmento "· ativos: X/Y" / "· X/Y do plano free" / "análises deste mês: X/Y" |
| Indisponível/erro | backend não confirma o número real (endpoint falha, timeout, resposta inválida) | fragmento numérico substituído por **"—"** (travessão), nunca um número estimado ou o último valor em cache silenciosamente reexibido como se fosse atual. Ver padrão existente `admin.usoIA.cotaPorUsuarioDia ?? "—"` (`App.jsx:5566`) — mesmo idioma, reaproveitado, não inventado |

Justificativa do estado "Indisponível": princípio 4 do `CLAUDE.md` ("se a
fonte de dados falhar... não invente valores; mostre o estado correto") e
critério de sucesso 3 da fase. O padrão "—" já é o idioma estabelecido do
repo para "não sei o valor agora" (contraste com `?? "ilimitado"`, que
significa "sei que não há limite" — semântica diferente, não intercambiável
com D-03/Pro).

## Fonte dos números — contrato de dados (não é UI, mas condiciona o que a UI pode exibir)

Esta seção formaliza o requisito de "duas fontes diferentes por desenho",
confirmado pelo `navigation-specialist` — **não é redundância a corrigir**,
é o padrão "status ambiente + status no ponto de decisão".

| Local | Fonte do numerador (contagem atual) | Fonte do denominador (limite) |
|-------|--------------------------------------|-------------------------------|
| Subtítulo Watchlist (visão passiva) | `data.watchlist.length` — estado **persistido/salvo** | `max_watchlist` do plano ativo (via endpoint novo desta fase ou campo equivalente) |
| `CatalogModal` (ponto de ação) | `catalogSel.length` — estado **local, em edição, ainda não salvo** (já usado hoje em `App.jsx:6618` como `catalogSel.length`/`data.catalog.length`) | mesmo `max_watchlist` do plano ativo |
| `AtividadeIAScreen` (análises do mês) | `monthUsed` de `/api/ai/quota` (já existe, `App.jsx` via `store.aiQuota()`) | `monthLimit` de `/api/ai/quota` (já existe) |

**Não compartilhar a mesma variável de estado entre subtítulo e
CatalogModal** — são semanticamente diferentes (salvo vs. em edição) por
desenho já existente no app; fazer o modal ler de `data.watchlist.length`
faria a contagem do modal divergir visualmente da seleção em progresso do
usuário antes de salvar.

### Contrato de resposta recomendado para o endpoint novo (watchlist quota)

Não vinculante quanto a rota/nome exato (`13-CONTEXT.md` deixa isso a
critério de quem planeja/implementa), mas os NOMES DE CAMPO abaixo são a
recomendação desta pesquisa para manter consistência com o padrão já
estabelecido em `/api/ai/quota` (`monthUsed`/`monthLimit` em nível raiz,
`server/app/main.py:461-479`):

```json
{ "count": 7, "limit": 10 }
```

`limit: null` = plano sem teto (Pro) → aciona o estado "Plano sem limite"
acima. Mesma semântica de `monthLimit: null` já usada em `/api/ai/quota`
para conta pro/anônima. O planner deve fazer `deviceStore` e `serverStore`
exporem um método com o MESMO nome nos dois lados (paridade — guardião
`web/tests/test_fase3_paridade_stores_generica.mjs`, que compara conjuntos de
nomes de método entre os dois `return {}` blocks), espelhando o padrão já
usado por `analisesNoMes()`/`aiQuota()` (leitura ao vivo do servidor, sem
contador paralelo no aparelho — D-05).

## iOS — contrato de enforcement (CAP-12, D-04/D-05)

Não é uma superfície visual nova, mas condiciona o comportamento visível:

- Antes de `deviceStore.addWatchlistTicker`/`putWatchlist` gravarem no
  `localStorage`, o método busca o limite real (mesma cadência de
  `analisesNoMes()`: chamada de rede a cada tentativa, sem cache — D-05).
- Se a busca falhar (offline, endpoint indisponível): **bloqueia a escrita**
  (fail-closed) e mostra a mensagem de indisponibilidade da tabela de
  Copywriting acima — nunca grava silenciosamente e nunca mostra erro
  genérico. Isto diverge deliberadamente do padrão fail-open de
  `A.analyze`/`App.jsx:7257` (aceitável lá porque o servidor é a autoridade
  real do gate; aqui, para watchlist, o cliente É a única linha de defesa
  contra o bypass do CR-01 reabrir — D-04).
- Se a busca confirmar `count >= limit`: bloqueia com a MESMA frase de
  recusa do backend (Fase 12), sem reinventar tom.
- Nenhum `10` hardcoded no front — sempre lido do endpoint novo (critério de
  sucesso 6).
