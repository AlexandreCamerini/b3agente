# Phase 35 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase boundary reminder:** this is hierarchy + progress copy layered on the
existing `OpcoesScreen.jsx`/`SecaoAnalisar.jsx`/`SecaoComparar.jsx` component
structure (`35-CONTEXT.md` `<domain>`) — not a redesign, not a new layout
primitive, not a reopened architecture decision. `35-CONTEXT.md` D-01..D-08
are locked; this document resolves what they leave implicit (exact copy,
exact render branch, exact TOKENS-array additions) and corrects two citation
errors found by direct read (flagged inline below, not re-litigations of the
decisions themselves). Where this document's own reasoning would extend a
locked decision's scope, it says so explicitly as a discretion note instead
of folding the extension silently into the decision's description.

### D-01/D-08 — Progress labels (porta → carril, 2 stages, never 3)

**Stage 1 — the read invite (`blocoLeituraDoServico`, `OpcoesScreen.jsx:540-563`).**
Its `Kicker` gains a stage suffix, using the existing `" · "` separator
convention already established for metadata suffixes in this file tree
(same separator D-06 uses for "leitura já feita" — one convention, not two):

```jsx
<Kicker>{(cp.opcoesLeituraTitulo || "LEITURA DO ATIVO") + " · " + (cp.opcoesPasso1de2 || "Passo 1 de 2")}</Kicker>
```

**Stage 2 — the pill row (`workspacePillRow`, `OpcoesScreen.jsx:637-655`).**
Today this row has no heading at all. Add a `Kicker` immediately above it,
inside `workspaceTopo` (`OpcoesScreen.jsx:695-707`), always visible once
`ticker` is truthy — confirmed by reading `SecaoAnalisar.jsx`'s guard logic
that the pill row itself is not gated by `temLeitura` (Analisar renders a
locked/lacunas state pre-leitura, not a hidden tab), so the stage-2 label is
constant, not conditional:

```jsx
<Kicker>{(cp.opcoesEscolhaTitulo || "O QUE FAZER") + " · " + (cp.opcoesPasso2de2 || "Passo 2 de 2")}</Kicker>
{temLeitura ? <div style={AJUDA}>{cp.opcoesLeituraConcluidaAjuda || "Leitura concluída — escolha Analisar ou Comparar."}</div> : null}
{workspacePillRow}
```

Placement: replace the current line `{workspacePillRow}` at
`OpcoesScreen.jsx:705` with the three-line block above. No new state — reads
`temLeitura`, already computed at `OpcoesScreen.jsx:419`.

**Never number Analisar/Comparar as 2/3** — this is D-01's explicit
guardrail (CLAUDE.md principle 5, cited in `35-CONTEXT.md` `<canonical_refs>`):
the stage Kicker text above ("O QUE FAZER") names the job, not a sequence
position, and the pill labels themselves (`cp.opcoesAbaAnalisar`/
`cp.opcoesAbaComparar`/`cp.opcoesAbaSetupsSalvos`) are untouched by this
phase.

### D-06 — "Leitura já feita" metadata line (new branch)

Today, once `temLeitura` is true, `podePedirLeitura` becomes false and
**nothing** renders in that slot (verified by reading the guard chain:
`podePedirLeitura = !!ticker && !leitura.dados && !leitura.carregando && !servicoIndisponivel` —
`leitura.dados` truthy makes it false). D-06 requires a Kicker-only
replacement there, gated **only** by `temLeitura` — D-06's own text ("o
bloco inteiro já desaparece quando `temLeitura` é verdadeiro... o Kicker...
ganha sufixo discreto") never mentions `abaWorkspace`, so the contract below
matches that literally, unconditional on which pill is active:

```jsx
{temLeitura ? (
  <div style={{ marginTop: "14px" }}>
    <Kicker>{(cp.opcoesLeituraTitulo || "LEITURA DO ATIVO") + " · " + (cp.opcoesLeituraJaFeita || "leitura já feita")}</Kicker>
  </div>
) : null}
```

**Discretion note, not part of the locked contract above:** this means the
"leitura já feita" line keeps rendering while the user is on the Setups
salvos pill, even though D-02's own reasoning ("convite de leitura...
nunca quando é Setups salvos") reads the same way here — it is metadata
about the same paid read, arguably irrelevant to that job. D-06 does not
extend its own gate to `abaWorkspace`, and this document does not silently
extend a locked decision on its own authority. If the planner or Alex
prefers `temLeitura && abaWorkspace !== "setups"` for consistency with D-02,
that is a one-token change to the condition above — flagged here for a
deliberate call, not decided by this document.

### D-03/D-04/D-05 — `BOTAO_PRIMARIO` (hierarchy)

**Correction to `35-CONTEXT.md` `<specifics>` before this is implemented —
the literal `color: "#fff"` value does not survive contact with the app's
own contrast rules and must not ship as written.** Verified by computing
WCAG contrast ratios from the real hex values in `App.jsx:95-213` (not
assumed):

| Theme × Mode | `T.accent` | White text (`#fff`) contrast | `T.onAccent` contrast |
|---|---|---|---|
| Dark · Estudo | `#2fa8a0` | **2.90:1 — FAILS AA (4.5:1)** | `#04231f` → 5.72:1 PASS |
| Light · Estudo | `#1f7d76` | 4.94:1 — passes, barely | `#ffffff` → 4.94:1 (identical) |
| Dark · Operador | `#d4af37` | **2.10:1 — FAILS AA** | `#241b06` → 8.09:1 PASS |
| Light · Operador | `#8a6c1c` | 4.94:1 (team-measured, `App.jsx:199-206` comment) | `#ffffff` → same |

The "Setups" sub-tab (where this phase's 3 pills live) is reachable in
**both** app modes (Estudo/Operador is the global `appMode` toggle,
independent of the Setups/Operar sub-tab split) — so all 4 rows above are
real, reachable states, not theoretical. Hardcoded white fails AA in 2 of 4.
`T.onAccent` is the token this design system already built and calibrated
for exactly this problem (`App.jsx` carries multiple dated comments —
"FIX-C16" — recording deliberate contrast remediation across this same
token family, and `T.onAccent` is already used this way at 20+ call sites in
`App.jsx` itself, e.g. lines 603, 722, 868, 902, 2146+); it is not a new
concept, it is the existing, correct one. **Use `T.onAccent`, not a literal
hex, for `BOTAO_PRIMARIO.color`.**

`CuradoriaEstruturas.jsx:268` (the cited precedent in D-03) itself hardcodes
`color: "#fff"` with no comment explaining the choice — read in full context,
it is not a considered exception, it is the same class of oversight this
correction fixes. Do not extend that specific line's literal value; extend
the *pattern* (accent fill, `border: none`, `opacity: 0.55` disabled) minus
the hardcoded color.

**Corrected constants:**

```js
const BOTAO_PRIMARIO = {
  minHeight: "44px", padding: "10px 14px", borderRadius: "11px",
  border: "none", background: T.accent, color: T.onAccent,
  fontWeight: 700, fontSize: "13px",
};
const desabilitadoPrimario = (cond) => (cond ? { opacity: 0.55, cursor: "not-allowed" } : null);
```

(`0.55` vs the existing `0.45` `desabilitado()` helper is correct as
specified in D-05 — verified precedent, `CuradoriaEstruturas.jsx:268`,
`opacity: executarTravado ? 0.55 : 1`.)

**TOKENS-array additions required** (mirror `onAccent` — already exposed at
`:root` by `App.jsx`'s existing `Object.entries(PALETTE[name])`/
`modeVarBlock` loop, `App.jsx:156,215`. Verified directly, not assumed:
`VARKEY("onAccent")` was run against the real transform function
(`App.jsx:153`, `(k) => "--" + k.replace(/[A-Z]/g, (c) => "-" + c.toLowerCase())`)
and produces `--on-accent`, with no special-casing anywhere in `App.jsx` —
`onAccent` already resolves correctly at 20+ existing call sites. No backend
or `App.jsx` change needed, only the local mirror per file below):

| File | Current `TOKENS` | Add |
|------|-------------------|-----|
| `OpcoesScreen.jsx:92-93` | has `accent`, `accentTint10` | `onAccent` |
| `SecaoAnalisar.jsx:42-43` | has `accent`, `accentTint10` | `onAccent` |
| `SecaoComparar.jsx:47` | **no `accent` today** | `accent`, `onAccent` |

**Applies to exactly 3 buttons** (D-04, verified by direct read, line ranges
current as of this research):
- "Ler no serviço de opções" — `OpcoesScreen.jsx:552-560`
- "Montar estrutura" — `SecaoAnalisar.jsx:320-329`
- "Ver possibilidades" — `SecaoComparar.jsx:152-161`

Every other button in scope (`SecaoSetups.jsx`, `WorkspaceHeader.jsx`
"Voltar", "Ver a cadeia"/"Ver as operáveis") keeps the neutral `BOTAO` —
unchanged, per D-04.

### D-07 — cost subtext inside `BOTAO_PRIMARIO` (corrected, resolved)

**Correction to `35-CONTEXT.md` D-07's citation:** the color-mix technique
is *not* already in production at `PropostaLastreada.jsx:254` — that file
has zero `color-mix` occurrences (verified: `grep -n "color-mix"
PropostaLastreada.jsx` returns nothing). The repo's only `color-mix` usages
are `CuradoriaEstruturas.jsx:254,307`, and they tint a **warning box
background** at 12% opacity (`T.warn` over transparent) — a different
technique for a different purpose (background tint, not translucent text
over a colored fill). There is no existing precedent in this codebase for
"white text at ~72% opacity over an accent-filled button."

**Computed, not assumed — the literal proposed value fails contrast in
every theme, not just the light theme D-07 flagged as unverified:**

| Theme × Mode | `T.accent` | `color-mix(#fff 72%, transparent)` effective contrast |
|---|---|---|
| Dark · Estudo | `#2fa8a0` | **2.20:1 — fails badly** |
| Light · Estudo | `#1f7d76` | **3.38:1 — fails** (needs 4.5:1 at 11px, not "large text") |

(Computed by alpha-compositing white-at-72%-opacity over each accent hex,
then measuring the resulting apparent color's contrast against that same
accent background — the two channels a translucent-white overlay actually
produces on screen. Dark/Light Operador would fail at least as badly given
their accent hues; not tabulated separately since the base-theme failures
already settle the recommendation below.)

**Resolution:** do not introduce alpha transparency for this text. The
codebase's own established de-emphasis technique for a secondary line next
to a primary label is an **opaque muted token + smaller size/weight** — see
`CUSTO_NO_BOTAO` itself (`OpcoesScreen.jsx:142-145`: `color: T.textMuted`,
`fontSize: "11px"` vs the label's `13px`/`fontWeight: 700`). Apply the same
principle with the accent-fill-safe token:

```js
const CUSTO_NO_BOTAO_PRIMARIO = {
  display: "block", fontSize: "11px", fontWeight: 600,
  color: T.onAccent, marginTop: "3px",
};
```

Because `T.onAccent` already clears 4.5:1 against its paired `T.accent` in
all 4 theme × mode combinations (table above), this passes at any font size
— WCAG's ratio requirement does not depend on size, only the size threshold
for the *minimum* ratio does, and this color already clears the stricter
(normal-text) minimum. **D-07's open risk is closed by this substitution —
no separate light-theme-only visual QA step is required**, but a quick
visual pass on ship is still good practice given this phase touches 3 CTAs
users will click on every workspace visit.

`marginTop: "3px"` matches `CUSTO_NO_BOTAO`'s existing value verbatim — not
a new spacing value.

### D-06 — completed-state mark for re-clickable CTAs (`MARCA_RESULTADO`)

Applies to "Montar estrutura" (`SecaoAnalisar.jsx`) and "Ver possibilidades"
(`SecaoComparar.jsx`) — never to "Ler no serviço", whose block disappears
entirely per existing behavior (unchanged).

```js
const MARCA_RESULTADO = {
  display: "flex", alignItems: "center", gap: "5px",
  fontSize: "11px", color: T.textMuted, marginTop: "6px",
};
```

Placement: between the button and the result block, rendered only when a
successful result exists (never on error/empty/loading — those already
render inside the existing cascade below):

- `SecaoAnalisar.jsx`: after the button (line 329), before the `carregando
  → erro → vazio → dados` cascade (line 331-332), condition
  `proposta.dados && (proposta.dados.estruturas || []).length`.
- `SecaoComparar.jsx`: after the button (line 161), before the
  `possibilidades` cascade (line 165-166), condition `possibilidades.dados
  && (possibilidades.dados.possibilidades || []).length`.

Content: `✓` + `T.textMuted` label text (proposed key
`cp.opcoesEstruturaMontada` / `cp.opcoesPossibilidadesVistas`, "Estrutura
montada" / "Possibilidades carregadas" — Claude's Discretion per
`35-CONTEXT.md`, adjust wording at plan time). **Never `T.positive`/
`T.negative`** — confirmed reserved for financial direction only
(`PropostaLastreada.jsx:183`, verified: `const cor = isCall ? T.positive :
T.negative; // NUNCA T.accent — mesma regra da manchete do ativo`).

`gap: "6px"` marginTop and `"6px"`/`"3px"` spacing values used above are
pervasive pre-existing conventions in this file tree (30+ occurrences
grepped across `web/src/opcoes/*.jsx`, e.g. `CandidatoOpcao.jsx:95`,
`PropostaLastreada.jsx:208,221`, `SecaoVigias.jsx:66-109`,
`CriarSetup.jsx:83,255,409`) — not new exceptions requiring fresh approval.

### JORN-03 parity — why `SecaoSetups.jsx` gets zero `BOTAO_PRIMARIO`

JORN-03 requires "the same clarity of steps" across all 3 pills, not
identical button treatment. Parity is satisfied at the **stage-2 Kicker**
level: "O QUE FAZER · Passo 2 de 2" renders above the pill row regardless of
which of the 3 tabs is active — a user on "Setups salvos" sees the exact
same progress framing as a user on "Analisar". `SecaoSetups.jsx` has no
analogous "next obligatory step" (it is a management job: view/create saved
setups, not a build-up toward a single reveal) — D-04 already settled this
by design, keeping its buttons neutral. Do not add a `BOTAO_PRIMARIO` inside
`SecaoSetups.jsx` looking for "parity"; parity is structural (the shared
Kicker), not per-button.

## Color

No new colors and no new CSS custom properties — `--on-accent` already
exists at `:root` for all 4 theme × mode combinations (`App.jsx:114, 149,
184, 212`, confirmed emitted automatically by `Object.entries(PALETTE[name])`/
`modeVarBlock`, `App.jsx:156, 215`, and confirmed resolvable by running the
real `VARKEY` transform against the string `"onAccent"` → `--on-accent`,
matching 20+ existing `T.onAccent` call sites in `App.jsx`). This phase only
extends 3 files' local `TOKENS` mirror arrays to read a variable that
already resolves correctly (table in the Layout section above).

**Extension of `34-UI-SPEC.md`'s accent reserved-for list (D-03, approved by
Alex):** accent gains a second usage form — solid fill (`BOTAO_PRIMARIO`),
distinct from the existing tinted-border form (active pill-row tab). Same
color token, different application, exactly as `34-UI-SPEC.md` documented
"nothing new gets accent" before this phase's approved extension.

| Role | Token | Usage |
|------|-------|-------|
| Dominant surface | `T.bgBase` | Unchanged |
| Secondary surface | `T.bgPanel` | Unchanged (`CAIXA`, `cabecalho`, `WorkspaceHeader`) |
| Accent — tinted (existing) | `T.accent` / `T.accentTint10` | Active pill-row tab border/tint/label (unchanged reserved-for from Phase 34) |
| **Accent — solid fill (new, D-03)** | `T.accent` background + **`T.onAccent`** text | `BOTAO_PRIMARIO`: exactly 3 CTAs — "Ler no serviço de opções", "Montar estrutura", "Ver possibilidades" |
| Destructive | `T.negative` | Unchanged — setup deactivation, not touched |

**Accent reserved for (extended list, supersedes `34-UI-SPEC.md`'s "nothing
new gets accent"):** (1) active pill-row tab state — border, tinted
background, label color (Phase 34, unchanged); (2) **NEW** solid fill +
`T.onAccent` text on exactly the 3 `BOTAO_PRIMARIO` CTAs named above.
Nothing else. `WorkspaceHeader`'s "Voltar" button stays neutral `BOTAO`
(Phase 34 decision, unchanged by this phase).

**`T.onAccent` vs the literal `#fff`/`color-mix` values proposed in
`35-CONTEXT.md` `<specifics>`:** see D-03/D-04 and D-07 sections above for
the full computed evidence. Summary: `color: "#fff"` fails AA (2.10:1–2.90:1)
in Dark·Estudo and Dark·Operador; `color-mix(#fff 72%, transparent)` fails
AA in every combination checked (2.20:1–3.38:1). `T.onAccent` passes in all
4 combinations (4.94:1–8.09:1) because it is the token this design system
already calibrated for text-on-accent-fill. **Use `T.onAccent`, not a
literal hex or `color-mix`, wherever text sits directly on `T.accent`
fill in this phase.**
