# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-rolled single-file React (`web/src/App.jsx`, ~7865 lines) |
| Icon library | none — Unicode glyphs used as status marks (`●`, `◔`, `⚠`, `◌`, `✓`, `✗`), consistent with `TIMING_STYLE` |
| Font | System sans (body/prose) + `MONO = "ui-monospace,'SF Mono',Menlo,Consolas,monospace"` (numeric/R-multiple values, established constant at `App.jsx:223`) |

**shadcn gate — deliberate override, not a skipped question.** `components.json` is absent, which would normally trigger the ask-Y/n gate. Overridden to N without asking because the project already has a mature, production, non-shadcn design system: a single 7865-line `App.jsx` with a full CSS-variable token system (`PALETTE.dark/light` × `MODE_OPERADOR.dark/light`, resolved through the `T.*` object), hand-rolled reusable primitives (`chip()`, `ConfluenceRing`, `TIMING_STYLE`/`REC_STYLE` badge-tuple patterns, `SetorAlvo` tap-to-explain affordance), and an explicit repo instruction (`CLAUDE.md`): "Não reescreva a aplicação sem necessidade. Não adicione funcionalidades fora do escopo pedido." Introducing shadcn for one phase that only adds badges/labels to existing screens would violate that instruction and fragment the token system. This phase extends the existing system; it does not introduce a new one.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap inside a new badge, vertical gap between stacked pills |
| sm | 8px | Gap between the histórico badge and the setup name/confluência value it sits next to |
| md | 16px | Gap between the histórico block and neighboring card sections (Radar/Watchlist row, setup list item) |
| lg | 24px | Not used in this phase (no new section-level container) |

Exceptions: **`4px 10px` pill padding** — the established convention for every existing badge/chip in this codebase (`chip()` at `App.jsx:2866`, `TIMING_STYLE` consumers). New histórico/aposentado/insuficiente pills MUST reuse this exact padding, not introduce a new one. This is a pre-existing pattern being matched, not a new decision. developer-approved — matches existing pattern — 2026-08-21

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Badge/pill label | 11px | 700 | 1.2 |
| Badge/pill value emphasis (R-multiple, %, n) | 11px | 800 | 1.2 (MONO font) |
| Body / explanatory sentence (concept sheet, tooltip) | 13px | 400 | 1.5 |
| Secondary metadata (timestamp, `medidoAte`, `janelaRef`) | 11px | 400 | 1.4 |

Weights declared: **400 (regular, prose/metadata)** and **700 (bold, labels)**. Exception, reused verbatim from the existing `chip()`/`ConfluenceRing` micro-convention: numeric values inside a badge render at **800**, one step bolder than the 700 label next to them, to visually separate "what this is" from "the number." This is an existing codebase pattern (`App.jsx:2869`, `App.jsx:5566`), not a new weight tier introduced by this phase. developer-approved — matches existing pattern — 2026-08-21

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `T.bgBase` | Card/page background (unchanged by this phase) |
| Secondary (30%) | `T.bgCard` / `T.bgPanel` | Existing card surfaces the new badges sit on top of |
| Accent (10%) | `T.accent` (mode-dependent: teal `#2fa8a0` in Estudo, gold `#d4af37` in Operador) | Reserved for: existing interactive/brand elements only (primary CTAs, active tab, `ConfluenceRing` mid-tier arc, the "Plano armado"/`◔` timing badge). **Do NOT use accent for the new histórico badges** — eligibility is a fact about the setup, not a brand/mode signal, and reusing accent would visually conflate "this is elegible" with "this is the app's highlight color," which is exactly the ambiguity the mode-color split (Brand Book v2) was built to avoid. |
| Destructive | `T.negative` (`#f26d6d` dark / `#c6464c` light) | Reserved for existing sell/negative-P&L usage. Not introduced for this phase — see semantic mapping below (negative eligibility uses `T.negative` too, but that is a factual-result color, not a destructive-action color; no destructive action is added in this phase). |

**New semantic mapping for this phase — all reused from existing tokens, zero new hex values:**

| State | Color pair | Rationale |
|-------|-----------|-----------|
| `elegivel === true` | `T.positive` / `T.positiveTint10` | Reuses `REC_STYLE["Estudar alta"]` pair — same visual weight as any other positive outcome in the app |
| `elegivel === false` | `T.negative` / `T.negativeTint10` | Reuses `REC_STYLE["Estudar baixa"]` pair — **same visual weight as positive**, not dimmed or de-emphasized. Non-negotiable per `didatica-boris` skill: no manipulation of visual weight between positive and negative results |
| Amostra insuficiente (`historico.insuficiente === true` OR `elegivel === null`, but `historico` exists) | `T.textFaint` / `T.bgBase` | Reuses the exact `TIMING_STYLE.sem_dado` pair — visually "no reading yet," never styled as negative. This is the critical distinction: insufficient evidence must look categorically different from negative evidence, not like a paler negative |
| Nunca medido (`historico` absent/`None`, or field key not present) | `T.textFaint` / `T.bgBase` | Same neutral pair as insuficiente — from the user's point of view these two states read identically ("no verdict yet"); the copy text is what differs |
| `aposentado === true` | `T.textMuted` on `T.bgCard`, with `T.borderDashed` outline (1px, dashed) | New visual treatment for this phase — a dashed border reused from the existing `borderDashed` token (already meaning "provisional/annotated" elsewhere in the app) to signal "archived, not a live candidate," clearly distinct from the solid-fill pills used for the other four states. Never overlaps with the negative-eligibility color — an aposentado setup does not also render as `elegivel === false` |
| Dado desatualizado (`medidoAte`/`calculadoEm` older than 2 business days) | Timestamp text drops to `T.textDim`, prefixed `⏱` | Modifier only — never repaints the badge's core color. A stale "elegível" badge stays visually positive; only the adjacent timestamp degrades. Per ADR-017 Decisão 2: "degrada visualmente, nunca bloqueia" |

Accent reserved for: primary CTAs, active nav/tab state, `ConfluenceRing` mid-tier stroke, `armado` timing badge — **explicitly not** the eligibility/histórico badges this phase adds.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (this phase has no new standalone CTA — it extends the existing tap-to-explain affordance) | Accessible label follows the existing `SetorAlvo` question format: `"O que é elegibilidade medida?"` / `"O que é setup aposentado?"` (mirrors the site-wide "O que é X?" screen-reader button pattern, `App.jsx:2297`) |
| Empty state (setup never measured) | Pill: **"Sem histórico medido ainda"**. Full sentence (concept sheet): *"Este setup ainda não tem sinais suficientes no ledger de 15 anos para medir desempenho — o número aparece assim que sinais forem resolvidos."* — this is a legitimate steady state, not a loading spinner (histórico arrives atomically with the `/api/scan` result; there is no separate async fetch to show a spinner for) |
| Empty state (insufficient sample, `n<40` in window) | Pill: **"Amostra insuficiente (n<40)"**. Full sentence: *"Menos de 40 sinais na janela atual — ausência de evidência não é prova de mau desempenho, só ainda não há dado suficiente."* |
| Error state | **Not applicable, by design.** `signal_ledger.historico_snapshot()` fails soft (catches its own exceptions, returns `{}`/last-good cache) and `setups._historico_map()` returns `None` on any failure — a provider outage is structurally indistinguishable from "never measured" and MUST render as the empty state above, never as a red error banner. This is intentional per the code's own comment ("informativo — a tela do usuário não pode cair por causa dele"); do not invent a distinct error UI for this field |
| Destructive confirmation | **Not applicable — no destructive UI action added.** The `entradaAuto` religamento is a backend data-driven gate flip (elegibilidade decide, not a user click), not a user-facing destructive control. The existing master "Entrada automática" toggle (Perfil/Config) is unchanged by this phase. See "Checkpoint humano" note below for the one required non-destructive transparency surface |

**Canonical phrases this phase must add** (none exist today — confirmed by CONTEXT.md and grep of `skill_ref.py`/`copy.js`). Follow the exact three/four-way mirror pattern already established for `TIMING` (`skill_ref.py` dict → `conceitos.py` `ROTULOS` mirror → `App.jsx` style-tuple → `copy.js` `COPY[modo]`), and extend `web/tests/test_vocabulario_espelho.mjs` with new assertions — do not assume existing assertions cover new keys automatically.

New `HISTORICO` dict (mirrors `TIMING` shape at `skill_ref.py:239-265`), one entry per state, both modes (`operador`/`educacional` in Python, `operador`/`estudo` in JS):

| State key | Operador voice | Estudo voice |
|-----------|----------------|--------------|
| `elegivel` | `"✓ ELEGÍVEL — vantagem estatística medida na janela {janela}."` | `"Estudo: vantagem estatística medida na janela {janela}."` |
| `inelegivel` | `"✗ NÃO ELEGÍVEL — sem vantagem estatística medida na janela {janela}."` | `"Estudo: sem vantagem estatística medida na janela {janela}."` |
| `insuficiente` | `"Amostra insuficiente (n<40) — ausência de evidência não é prova de mau desempenho."` | same text, both modes (fact, not opinion) |
| `nunca_medido` | `"Sem histórico medido ainda."` | same text, both modes |
| `aposentado` | `"Padrão gráfico identificado, sem vantagem estatística medida (ADR-016)."` | same text, both modes — this exact phrase is already specified verbatim in `08-CONTEXT.md` |
| `desatualizado` (modifier, appended to timestamp, not a standalone state) | `"Medido até {medidoAte} — dado pode estar desatualizado."` | same text, both modes |

Mandatory paired-numbers sentence (ADR-017 Bloco 2 contrast — use **only if** this phase's planning includes surfacing the "why Operador is now restricted" explanation; never split the two numbers):

> `"Sem filtro: −0,099R por sinal (todos os setups, 15 anos) · Com filtro (setups elegíveis na janela anterior): +0,005R — estatisticamente um empate, não lucro."`

Static string, not parametrized — these are the fixed ADR-017/ADR-016 backtest reference numbers, not a live computation; do not wire this to a live endpoint that could drift from the cited figures without an ADR update.

Entrada automática gate transparency (extends the existing "card de status único" from FIX-C19, Operador tab — additive row, not a new toggle):

- `"Entrada automática disponível para {setup} — elegibilidade medida em {janelaRef}."`
- `"Entrada automática bloqueada para {setup} — sem vantagem estatística medida nesta janela."`

**Checkpoint humano note (transparency, not a confirmation dialog):** per `08-CONTEXT.md`, religando `entradaAuto` is a real-behavior change to automatic simulated-money execution and requires a human checkpoint before production deploy (same pattern as `07-06`). This is a deploy-process gate, not a runtime UI confirmation — no new modal/dialog is specified for the end user. The transparency requirement this phase DOES own is: the existing per-order toast/log copy (`toastCompra`, already mode-aware) must remain accurate for auto-executed entries so the user can see, after the fact, that an entry fired and (via the status-card row above) why it was allowed to.

**Deferred item resolved:** `08-CONTEXT.md`'s `<deferred>` block flags "prompt de IA elaborado explicando expectância/R-múltiplo em profundidade... avaliar no planejamento se cabe nesta fase" as an open planning question, not a locked decision — out of scope for this UI-SPEC to resolve. If the planner brings a new AI narration surface into this phase, the **Guardrail explícito** from `08-CONTEXT.md` applies unconditionally: the prompt may only narrate numbers the backend already computed (never rank, select, or judge a setup), and if it cites the sem-filtro/com-filtro contrast, both numbers must appear together, exactly as specified above — never the positive number in isolation.

## Interaction & State Inventory (supplements the template — required by CLAUDE.md princípio 9)

Every histórico/eligibility surface added by this phase must implement all four states below; none is optional:

1. **Nunca medido** (`historico` absent/`None`) — neutral pill, "Sem histórico medido ainda."
2. **Amostra insuficiente** (`historico.insuficiente === true` OR `elegivel === null` with `historico` present) — neutral pill (same visual family as #1), "Amostra insuficiente (n<40)." Never styled as negative.
3. **Dado desatualizado** (`medidoAte`/`calculadoEm` older than 2 business days) — visual modifier only (dimmed timestamp, `⏱` prefix), layered on top of whichever of the other three/five states applies; never its own pill, never blocks reading the underlying number.
4. **Aposentado** (`s.aposentado === true`) — dashed-border tag, distinct from all of the above; setup stays in the list (never removed), number stays visible next to it.

Plus the two measured-eligibility states (elegível / inelegível) from the Color table above — six renderable states total per setup, all reachable, none collapsed into another to save a component variant.

**Where these render** (per `08-CONTEXT.md` canonical refs, confirm exact line numbers at implementation time — file has been edited since research):
- Radar/Watchlist ticker row: `setupElegivel`/`setupHistorico` next to `melhorSetup`/`confluencia%` (`App.jsx` ~1734, ~1796, ~5776-5790).
- Setup list item inside the ativo card: `s.historico`/`s.aposentado` next to `s.nome`/`s.confluencia%` (`App.jsx` ~5873).
- Operador status card: new row for `entradaAuto` per-setup gate state (extends FIX-C19 card, exact location TBD by planner — not yet built when this contract was written).

**Focal point (Dimension 2 recommendation):** on all three screens, the new histórico/eligibility pill is a SECONDARY signal — it never competes with the primary anchor for first-read priority.
- Radar/Watchlist ticker row: `melhorSetup` + `confluencia%` (via `ConfluenceRing`) stays the first thing the eye lands on; the histórico pill sits adjacent/below, read second.
- Setup list item inside the ativo card: `s.nome` + `s.confluencia%` stays the primary anchor; `s.historico`/`s.aposentado` renders as a trailing pill, read after the setup name.
- Operador status card: the existing gate summary (Modo do app · Operador no servidor · Executar/sinalizar, FIX-C19) stays the primary anchor; the new per-setup eligibility row is an additional line below it, not a replacement of the existing focal hierarchy.

**Accessibility:** every new pill needs a screen-reader-readable equivalent of its visual glyph (`✓`/`✗` are not SR-friendly alone) — reuse the existing `role="img" aria-label` pattern from `ConfluenceRing` (`App.jsx:5562`) or the `SR_ONLY` + "O que é X?" button pattern from `SetorAlvo` (`App.jsx:2299-2306`), do not ship a bare Unicode glyph with no text alternative.
