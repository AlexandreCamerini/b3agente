# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Scope: evolve `OpcoesCamada` (`web/src/App.jsx:2970`) inside `AtivoCard` from a
pure chain browser into **proposta pronta + cadeia expansível**, for the two
lastreadas operations (venda de CALL coberta, compra de PUT de proteção).
Reuses the existing "Hero reconciliado v11" decision-card language (manchete
única + chips) — does not invent a new visual system. No shadcn/Tailwind in
this codebase; the design system is a hand-rolled token object (`T`, from
`PALETTE`/`MODE_OPERADOR` CSS variables) consumed via inline `style={}}` across
a single 7600-line `web/src/App.jsx`.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — deliberate, see rationale below |
| Preset | not applicable |
| Component library | none (hand-rolled React components, no Radix/base-ui) |
| Icon library | none — emoji glyphs used as icons (⚡, 📈, ▾) and CSS-drawn shapes |
| Font | system stack (no `font-family` override found at root) for body text; `MONO = "ui-monospace,'SF Mono',Menlo,Consolas,monospace"` for all numeric/ticker/price values |

**Rationale for skipping the shadcn gate:** `components.json` is absent, but
the project already has a deliberate, mature design system that predates and
is incompatible with shadcn's shape: a `PALETTE` token object (dark/light ×
Estudo/Operador = 4 combinations) emitted as CSS custom properties, consumed
through a `T` proxy object (`T.accent`, `T.bgCard`, …) so no call site ever
hardcodes a hex. Contrast ratios are measured and commented inline (WCAG AA
guardrail, `test_brand_book_v2_tokens.mjs`). Introducing shadcn now would
fracture 7600 lines of established convention for no concrete gain — CLAUDE.md
requires a one-line justified gain to deviate from an established baseline,
and staying on the existing token system is the side of that rule that
applies here. Phase 14 adds new UI elements as new functions inside
`App.jsx`, using the same `T` token object and the same inline-style
convention as every existing component in the file (`OpcoesCamada`,
`AtivoCard`, `OpcaoContrato`).

## Spacing Scale

Declared values for **phase 14's new elements only** (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps inside the trava-de-lastro badge and liquidação notice |
| sm | 8px | Gap between chips/badges in the proposal card's chip row; gap between proposal card and the "ver cadeia completa" toggle below it |
| md | 16px | Internal padding of the proposta card body (`padding: "16px"`, replaces the ad hoc `9px 11px` of the base hero for this specific new card so it reads as a distinct, larger decision surface) |
| lg | 24px | Vertical separation between the proposal card and the expandable chain accordion (`OpcoesCamada`) below it |

Exceptions: `OpcoesCamada` (`App.jsx:2970`), `AtivoCard`'s hero block
(`App.jsx:3018`), and `OpcaoContrato` (`App.jsx:2901`) predate this contract
and use a finer ad hoc px scale (6, 7, 9, 10, 11, 14, 15, 20, 34px). Phase 14
does **not** retrofit that scale — it is left exactly as-is where reused
unmodified (the chain accordion rows, the liquidity badge, the breakeven
grid). Only the new proposal card, trava badge, and liquidação notice follow
the 4/8/16/24 scale above.

## Typography

Declared for phase 14's new elements (existing reused components — chain
rows, breakeven grid — keep their current sizes unchanged, see Exceptions):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 12px | 400 | 1.5 |
| Label | 10px | 800 | 1.3 |
| Heading | 13px | 800 | 1.3 |
| Display | 17px | 800 | 1.3 |

- **Body (12/400/1.5):** didactic/explanatory copy inside the proposal card
  (Estudo's "se você tivesse feito isso…" sentence, the risk disclaimer line,
  the liquidação-forçada explanation). Matches the existing disclaimer line
  style in `OpcaoContrato` (`fontSize: "10.5px"`, unbolded) scaled up slightly
  for a primary-surface card instead of a nested accordion row.
- **Label (10/800/1.3):** uppercase eyebrow labels — `"PROPOSTA · VENDA
  COBERTA"`, `"PROPOSTA · PUT DE PROTEÇÃO"`, the trava-de-lastro badge text
  (`"N AÇÕES TRAVADAS"`), letter-spacing `0.04em` (reuses the exact eyebrow
  treatment already used for `"DECISÃO DA MESA"` / `"PLANO EDUCACIONAL"` at
  `App.jsx:3172`).
- **Heading (13/800/1.3):** the proposal's structural line — contract +
  quantity + strike (`"3× CALL PETR4 · strike 38,50"`), rendered in `MONO`.
  Same weight/role as the existing contract-row headline in `OpcaoContrato`
  (`App.jsx:2915`, `fontSize: "12.5px"`).
- **Display (17/800/1.3):** the proposal's manchete única — the one
  deterministic-motor sentence stating the proposed operation in plain PT-BR
  (e.g. `"Vender 3 calls de PETR4 por R$ 1,85"`). Identical size/weight to the
  existing hero manchete (`App.jsx:3173`, `fontSize: "17px", fontWeight: 800`)
  — this is a deliberate visual echo: the options proposal is a sibling of
  the stock decision, not a separate genre of card.

Weights: exactly 2 declared for new elements — **400** (regular, Body only)
and **800** (bold, Label/Heading/Display). The reused `OpcaoContrato` rows
and the reused `AtivoCard` chip row keep their existing **700** weight —
pre-existing, not retrofitted. These will render in the same card as the new
400/800 elements (the proposal card sits above the unmodified chain
accordion, and above/below the unmodified chip row), so 700 and 800 will
appear as visual neighbors in the assembled card. This is an accepted
exception, not a contradiction to resolve: 700 (chips/chain, pre-existing)
and 800 (proposal card, new) read as two intentionally different surfaces —
chips are compact inline tags, the proposal card is the primary decision
surface — the weight difference reinforces that hierarchy rather than
clashing. The executor should not change 700 to match on the pre-existing
elements.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `T.bgBase` — dark `#10121a` / light `#f7f8fc` | App background behind all cards |
| Secondary (30%) | `T.bgCard` — dark `#1b1f2e` / light `#ffffff` (nested surfaces: `T.bgBase` again, used as the inset panel background for the chain accordion, per existing `OpcoesCamada` pattern) | The proposal card surface, the `AtivoCard` shell, the chain accordion panel |
| Accent (10%) | **Mode-dependent — not a single hex.** Estudo: dark `#2fa8a0` / light `#1f7d76`. Operador: dark `#d4af37` / light `#8a6c1c` | See "Accent reserved for" below |
| Destructive/negative | `T.negative` — dark `BRAND.red` / light `#c6464c` | Closing/selling actions, the forced-liquidation notice, the trava-de-lastro warning icon |

The template's single-cell accent row does not fit this codebase: accent is a
**mode axis**, not a constant. `T.accent` resolves to teal in Estudo and gold
in Operador via a CSS-variable override (`MODE_OPERADOR`), and the same
proposal card must render correctly under both without any code branch —
this is exactly what `T.accent` already guarantees. Do not hardcode either
hex; use `T.accent`.

Accent reserved for (phase 14 additions):
- The `"PROPOSTA · …"` eyebrow label color
- The primary CTA button border/background tint (`T.accentTint`) for
  "Vender CALL coberta" / "Comprar PUT de proteção" in Operador mode
- The expand/collapse chevron on the proposal card when it links to "ver
  cadeia completa" (mirrors the existing chevron treatment in `OpcoesCamada`)

Accent is explicitly **not** used for the manchete única / verdict text —
that follows the existing house rule (`App.jsx:768-773`): the deterministic
verdict color is always semantic (`T.positive`/`T.negative`/neutral
`T.textFaint`), never `T.accent`, because the accent hue changes between
modes and the verdict must read identically regardless of mode. For the
options proposal, apply the same rule: the manchete color follows
call/put polarity via `T.positive` (premium received, CALL) /
`T.negative` (protection cost, PUT) exactly like existing chain rows already
color CALL/PUT (`App.jsx:2916`), not `T.accent`.

Positive (`T.positive`) is used for premium received / CALL context; negative
(`T.negative`) for cost paid / PUT context and any locked/destructive state —
this reuses the existing polarity already established in `OpcaoContrato`
(`c.optionType === "call" ? T.positive : T.negative`), unchanged.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (Operador, CALL) | Imperative register per `vocab["operador"]` (mesa, ordem de ação): static label `"Vender CALL coberta"`; live label follows the existing dynamic-price pattern (`"Comprar — R$ X (100 cotas)"` at `App.jsx:2957`) → `"Vender N× CALL {TICKER} · strike {K} — recebe R$ {prêmio}"` |
| Primary CTA (Operador, PUT) | Imperative register: static label `"Comprar PUT de proteção"`; live label `"Comprar N× PUT {TICKER} · strike {K} — custa R$ {prêmio}"` |
| Empty state heading | `"Sem proposta agora"` |
| Empty state body | No lastro: `"Sem posição em {TICKER} na carteira — venda coberta e put de proteção exigem uma posição real do ativo-lastro."` No setup técnico elegível: `"A leitura técnica de {TICKER} não indica venda coberta nem put de proteção agora. A cadeia completa continua disponível abaixo."` |
| Error state | Reuses the existing ADR-004 degraded-provider phrasing verbatim: `"Cotação de opções indisponível no momento. Tente novamente em alguns minutos."` For the proposal CTA specifically (blocked, not just chain): `"Proposta indisponível — cotação de opções degradada."` (mirrors `OpcaoContrato`'s existing `"Indisponível — cotação de opções degradada"` button-disabled label at `App.jsx:2957`) |
| Destructive confirmation — abrir CALL coberta | `window.confirm` (same mechanism as `resetPortfolio`, `App.jsx:6568`): `"Vender {N} call(s) de {TICKER} trava {qty} ação(ões) do seu lote-lastro até você recomprar a call ou ela vencer. Continuar?"` |
| Destructive confirmation — fechar CALL coberta antes do vencimento | `"Recomprar esta call por R$ {custo} destrava {qty} ação(ões) de {TICKER} imediatamente. Continuar?"` |
| System notice — liquidação forçada (não é ação do usuário, é estado) | `"Esta call de {TICKER} venceu dentro do dinheiro e não foi fechada a tempo — liquidada em dinheiro pelo valor intrínseco (R$ {valor}). Sua posição em ações não foi alterada."` — informativo, sem CTA, cor `T.negative` no ícone/borda, texto em `T.textSecondary` (nunca dramatizado com vermelho no texto inteiro — mantém o padrão de "resultado sem manipulação visual" do CLAUDE.md). A fórmula exata de `{valor}` (valor intrínseco) é Claude's Discretion do planejamento — este contrato define só a copy, não o cálculo. |
| Estudo — mesma proposta, sem CTA | Conditional/descriptive register per `vocab["educacional"]` (nunca ordem): `"Se você tivesse vendido esta call coberta agora, receberia um prêmio de R$ {prêmio} e travaria {qty} ação(ões) até a recompra ou o vencimento."` / `"Se você tivesse comprado esta put de proteção agora, pagaria R$ {prêmio} para proteger {qty} ação(ões) contra queda abaixo de R$ {strike}."` |
| Trava de lastro — badge na Carteira | `"{qty} travada(s) · lastro de CALL"` (reaproveita o estilo de `PosPill`, `App.jsx:1023-1026`, cor `T.negative` em vez de `T.accent` porque comunica restrição, não posição neutra) |

Naming note (Claude's Discretion per CONTEXT.md): the operation is labeled
**"venda coberta"** and **"put de proteção"** in UI copy, consistent with the
phase name and with existing PT-BR product vocabulary (`vocab["educacional"]`/
`vocab["operador"]` pattern in `skill_ref.py`) — not "covered call"/"protective
put" (no untranslated finance jargon elsewhere in the product). This naming
should be confirmed against `skill_ref.py`'s canonical vocabulary structures
at planning time (per the didatica-boris skill: "texto novo entra nessas
estruturas, não solto no front"); the Operador/Estudo register split above
(imperative vs. conditional) already follows the non-negotiable rule in that
skill file and is not itself a discretion item.
