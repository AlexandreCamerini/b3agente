# Phase 23 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** finishing phase, not exploration (`23-CONTEXT.md`, `<specifics>`:
"Nenhuma referência visual nova além do que já existe no app... Fase de

## Discrepancy Report — MOTION-02 has two gaps CONTEXT.md's binary framing missed

### Gap 1 — no sequencing point for "before success state"

`23-CONTEXT.md` says the pulse fires "ANTES de a UI trocar para o estado de
sucesso definitivo (o card/toast/mensagem que já existe hoje)." The actual
code (`App.jsx:8222-8250` `confirmBuy`, `App.jsx:8165-8184` `confirmSell`)
does this in one synchronous burst once the await resolves:

```js
const s = await store.buy(bm.t, bm.qty, bm.meta || undefined);
setData(s); setBuyModal(null);      // modal unmounts HERE
flash(cp.toastCompra(bm.qty, bm.t)); // toast fires HERE, same tick
```

There is no gap between "order confirmed" and "modal gone / toast shown" for
a 120ms pulse to play in. The value that should pulse — `money(cost)` in
`BuyModal` (`App.jsx:7517`, the "Custo estimado" row) / `money(valor)` in
`SellModal` (`App.jsx:7611`, the "Valor estimado" row) — is about to unmount
at the exact moment `store.buy`/`store.sell` resolves.

### Gap 2 — the resolve path is not binary; it has a `pendente` branch that must NOT pulse

`23-CONTEXT.md` frames the outcome as "sucesso ou rejeição, nunca parcial."
That is true for the ORDER'S fill semantics (guardrail, `CLAUDE.md`), but the
UI's own resolve path has a third branch the requirement text does not name:
`confirmBuy`'s `try` block checks `s.pendente` (`App.jsx:8230-8242`) — when
the market is closed, the order is accepted but NOTHING executed yet, no
position is created, and the UI shows `cp.toastOrdemPendente(...)` +
`BuyModal`'s own "PENDENTE" pill (`App.jsx:7495`, `ctx.cp.ordemPendentePill`)
instead of the executed-order toast. `confirmSell` mirrors this exactly
(`App.jsx:8175`, `st.pendente ? cp.toastOrdemPendente(...) :
cp.toastVenda(...)`). This project has already had to correct the identical
confusion once, for analytics tracking (`App.jsx:8172-8174`/`8227-8228`,
comment: "analítica não pode confundir ordem PENDENTE... com compra
concluída"). Pulsing the value on a `pendente` resolve would repeat that
exact mistake visually — telling the user "this executed" via a
success-flavored animation when nothing executed. This is not a style
nitpick: `CLAUDE.md` principle 9 lists "ordem pendente"/"mercado fechado"
and "operação concluída" as distinct required states.

**Resolution (required contract, not left to planner discretion):**

1. On resolve, branch on `s.pendente` (`confirmBuy`) / `st.pendente`
   (`confirmSell`) BEFORE deciding whether to pulse:
   - `pendente === true`: **no pulse.** Go straight to
     `setBuyModal(null)`/`setSellModal(null)` + `flash(cp.toastOrdemPendente(...))`
     exactly as today — zero code change to this branch beyond what Gap 1's
     restructuring requires it to still reach.
   - `pendente` falsy (order actually executed): proceed to the pulse
     sequence below.
2. For the executed branch: do NOT call
   `setBuyModal(null)`/`setSellModal(null)` immediately. First flip a local
   flag on the modal state (e.g. `setBuyModal((b) => ({ ...b, confirmado:
   true }))`) — this keeps the modal mounted for one more render.
3. `BuyModal`/`SellModal` render the cost/value node with a pulse
   class/style when `confirmado` is true (see Motion Contract → MOTION-02
   below for the exact keyframe).
4. After the pulse duration elapses, THEN call `setBuyModal(null)` (or
   `setSellModal(null)`) and fire `flash(cp.toastCompra(...)/toastVenda(...))`
   — the existing toast becomes the terminal success state, unchanged in
   copy or trigger condition, just delayed by the pulse's own duration.
5. **Respect `prefers-reduced-motion` in the JS delay itself, not only in
   CSS** — the module already computes this exact boolean at
   `App.jsx:1443` (`REDUCE_MOTION`), consumed today at `App.jsx:1637` to
   skip a `transition` under reduced motion. Reuse `REDUCE_MOTION` here: if
   `true`, skip the pulse render entirely and call
   `setBuyModal(null)`/`flash(...)` immediately (0ms wait) — otherwise the
   CSS animation would correctly render instantly (0.01ms, per the global
   rule) but the JS `setTimeout` would still hold the modal open for
   ~120ms of dead time with nothing visibly happening, which is exactly the
   kind of "still animates, just invisibly" bug the reduced-motion
   requirement exists to prevent (ROADMAP success criterion 3: "o estado
   final aparece direto, sem perda de informação" — direto means no delay,
   not just no visible motion).
6. Order rejection (`catch` branch, `App.jsx:8244-8249` / `8176-8183`) is
   UNCHANGED — no `confirmado` flag, no pulse, immediate `flash("Compra: "
   + ...)`/`flash("Venda: " + ...)` exactly as today. This is what
   `23-CONTEXT.md` already mandates ("Ordem rejeitada... NÃO pulsa") —
   flagged here only to confirm the reject path needs zero code change.

Net: the pulse fires on exactly one of the three outcomes — executed. Both
`pendente` and rejected skip it, each reaching its own existing, unchanged
toast immediately.

This turns a "sounds simple, has no attachment point, and undercounts its
own outcomes" requirement into an exact, implementable sequence. See Motion
Contract → MOTION-02 for the keyframe/timing values.

| Broad `prefers-reduced-motion` gate (`.b3, .b3 *, .b3 *::before, .b3 *::after {transition-duration:0.01ms!important; animation-duration:0.01ms!important; animation-iteration-count:1!important;}`) | `App.jsx:384` | developer-approved — matches existing pattern — 2026-09-06 |
| `REDUCE_MOTION` JS boolean (module-level, `window.matchMedia("(prefers-reduced-motion: reduce)").matches`) | `App.jsx:1443`, consumed at `App.jsx:1637` | developer-approved — matches existing pattern — 2026-09-06 |

### MOTION-01 — new-setup card entry

- **Target element:** `AtivoCard`'s own root `<div key={t} id={"ativo-"+t}
  style={{...card, padding:"14px 15px"}}>` (`App.jsx:3438`) — this is a
  single root element per card, confirmed by direct read; the animation
  attaches here, inside `AtivoCard` itself, not at either call site
  (`App.jsx:3896` Watchlist, `App.jsx:6913` Radar/Mesa).
- **New prop:** `AtivoCard` accepts a new boolean, e.g. `isNovo` (name is
  implementer's choice per `23-CONTEXT.md`'s Claude's Discretion), computed
  by each caller from a `useRef<Set<string>>` of tickers already rendered in
  THIS list during THIS mount (per `23-CONTEXT.md`: "reseta ao trocar de
  tela ou recarregar" — do not persist to `localStorage`/server). The ref is
  updated (ticker added to the set) on every render pass, AFTER computing
  `isNovo` for the current pass — so a ticker is `isNovo` exactly once, on
  the render where it first appears.
- **Keyframe (new, add to `GlobalStyle()`):**
  ```css
  @keyframes b3cardEnter{ from{ opacity:0; transform:translateY(8px); } to{ opacity:1; transform:translateY(0); } }
  .b3 .card-enter{ animation:b3cardEnter 200ms ease-out; }
  ```
  Naming follows the existing `b3*` keyframe convention (`b3spin`,
  `b3shimmer`, `b3tt` at `App.jsx:359-364`).
- **Duration/easing:** 200ms, `ease-out` — matches `23-CONTEXT.md`'s target
  exactly (~200ms). `translateY(8px→0)` matches the "ex.: 8px→0" example
  given in `23-CONTEXT.md`; this is the recommended literal value (not just
  an example) since it is the smallest 4px-multiple that reads as a visible
  "settle" without a large layout jump.
- **Application:** `className: isNovo ? "card-enter" : undefined` on the
  root div (or an inline `animation` style if the planner prefers, per
  `23-CONTEXT.md`'s explicit "escolha de organização do planner" — either
  falls under the reduced-motion rule the same way since both use CSS
  `animation`).
- **Non-triggering case:** re-renders of a ticker already in the seen-set
  (e.g. price tick updates the same card) must NOT re-apply `isNovo` — the
  animation is entry-only, never a re-mount/re-flash on data change. Since
  `isNovo` is computed once per ticker per session (per the ref logic
  above) and React does not remount the same `key={t}` element, the CSS
  animation naturally plays once per element lifetime as long as the
  `card-enter` class is only present on the render where `isNovo` is true
  — if the planner instead keeps the class attached on every render for a
  ticker that started `isNovo`, React needs an explicit one-shot guard
  (e.g. drop the class after the animation's `onAnimationEnd`, or key the
  class off a boolean that only reads true on first paint). Flag this for
  the plan's acceptance check: **verify by re-rendering with a price change
  after the entry animation has played — the card must NOT visibly
  re-animate.**

### MOTION-02 — order-confirmation value pulse

- **Target elements:** `BuyModal`'s "Custo estimado" value (`App.jsx:7517`,
  `{money(cost)}`) and `SellModal`'s "Valor estimado" value (`App.jsx:7611`,
  `{money(valor)}`) — see Discrepancy Report above for the required
  sequencing change and the `pendente` gate that make this pulse correct.
- **Keyframe (new, add to `GlobalStyle()`):**
  ```css
  @keyframes b3valuePulse{ 0%{ transform:scale(1); } 50%{ transform:scale(1.08); } 100%{ transform:scale(1); } }
  .b3 .value-pulse{ animation:b3valuePulse 120ms ease-out; display:inline-block; }
  ```
  `display:inline-block` is required for `transform:scale()` to apply
  visibly on an inline `<span>` (both target nodes are `<span>` elements,
  `App.jsx:7517`/`7611`) — without it the scale transform on an inline
  element is a no-op in most browsers.
- **Duration/easing:** 120ms, `ease-out` — matches `23-CONTEXT.md`'s target
  exactly (~120ms), `scale(1→1.08→1)` matches its literal example.
- **Application:** the `confirmado` flag from the Discrepancy Report
  resolution drives `className: confirmado ? "value-pulse" : undefined` on
  the target `<span>`. The `setTimeout` that finally closes the modal must
  wait for the pulse's own duration — reuse the same literal `120` (ms) so
  the two numbers never drift apart. **Gate order matters: check `pendente`
  first, `REDUCE_MOTION` second** — a pending order never pulses regardless
  of the reduced-motion setting, because it isn't the executed/success case
  at all. This sketch elides one existing line for brevity — the
  `track("trade_simulated", {...})` analytics call
  (`App.jsx:8229`/`8174`) is NOT removed by this change; it stays exactly
  where it is today, immediately after `setData(s)`, in both branches:
  ```js
  const s = await store.buy(bm.t, bm.qty, bm.meta || undefined);
  setData(s);
  track("trade_simulated", { side: "buy", ticker: bm.t, instrument: "equity", pendente: !!s.pendente }); // unchanged, existing call
  const finish = () => {
    setBuyModal(null);
    if (s.pendente) { flash(cp.toastOrdemPendente(bm.qty, bm.t)); }
    else {
      flash(cp.toastCompra(bm.qty, bm.t));
      setStopAlvoFor(bm.t); A.runStopAlvoFor(bm.t); // unchanged, existing N3 offer
    }
  };
  if (s.pendente || REDUCE_MOTION) { finish(); }
  else { setBuyModal((b) => ({ ...b, confirmado: true })); setTimeout(finish, 120); }
  ```
  (Sketch for `confirmBuy`; `confirmSell` mirrors it with `setSellModal`/
  `st.pendente`/`cp.toastVenda`/its own existing `track(...)` call at
  `App.jsx:8174`.)
- **Non-triggering cases:**
  1. **Rejected** (`catch` branch) — unchanged, no `confirmado` flag ever
     gets set, so `.value-pulse` never applies to a failed confirmation.
     Enforced by construction (the flag is only reachable from the `try`
     block's resolve path).
  2. **Pendente** (market closed, nothing executed) — the `s.pendente`
     check above short-circuits to `finish()` immediately, same as the
     `REDUCE_MOTION` case, so the pulse never fires and the existing
     `ordemPendentePill`/`toastOrdemPendente` flow is untouched. **Verify:**
     trigger a buy/sell while the market is closed (or with a mocked
     `pendente:true` response) and confirm the value node shows zero
     animation and the modal closes with the pending toast exactly as
     before this phase.

## Illustration Contract (ILUS-01)

  component swap.
- **Fixed elements, not themeable, not mode-dependent** (locked by the
  `LogoMark` comment this phase must preserve, `App.jsx:202-205`):
  glasses always `BRAND.amber`, face/body always `#2a3a6b`, regardless of

  or any theme-conditional token — this is the exact regression `LogoMark`'s
  own comment says v2 already closed once ("Até a Fase 3 os óculos/bico/selo
  seguiam o acento do MODO... v2 fecha essa porta").
- **Discretionary details** (per `23-CONTEXT.md`, left to implementer):
  body proportion, whether a "necktie" accent (as the current PNG has) is
  included, whether feet are drawn — none of these are locked, as long as
  the result is unambiguously the same character as `LogoMark`/the app icon
  side-by-side (ROADMAP success criterion 4).

**Integration point:** `BorisIntro.jsx:34` (`<Boris size={110}/>` inside the

**Out of scope (explicit, from `23-CONTEXT.md`/`deferred`):** unifying

## Decisions

### 1. MOTION-02 sequencing gap + pendente gate — resolved (see Discrepancy Report)

`confirmBuy`/`confirmSell` gain a one-render `confirmado` flag and a 120ms
`setTimeout` (skipped entirely when `s.pendente` is true OR `REDUCE_MOTION`
is true) before closing the modal and firing the existing toast. This is
required implementation detail, not an open question — `23-CONTEXT.md`
specified the visual effect assuming a binary success/reject outcome, but
the real resolve path has a third (`pendente`) branch that must be excluded
from the pulse to avoid visually claiming an unexecuted order succeeded.
Full contract in Discrepancy Report and Motion Contract → MOTION-02 above.

### 2. Reuse of `LogoMark`'s exact color/geometry vocabulary for ILUS-01 — approved

Pre-authorized by `23-CONTEXT.md` directly ("reusando o MESMO vocabulário
visual já estabelecido em `LogoMark`") and by the orchestrator's own framing
of this task. Every literal color value is cited against its `LogoMark`
source line in the Color section above with the
`developer-approved — matches existing pattern — 2026-09-06` sign-off,
following the exact row-level citation granularity `21-UI-SPEC.md`/
`22-UI-SPEC.md` used for their own reuse decisions — not a one-time blanket
note.

### 3. Reuse of Phase 20's `prefers-reduced-motion` CSS rule verbatim — approved

Pre-authorized by `23-CONTEXT.md` directly ("Não reabrir essa regra — os
dois motions novos DEVEM cair dentro dela automaticamente") and by the
orchestrator's own framing of this task. No new `prefers-reduced-motion`
block is introduced; both new `@keyframes` blocks are plain CSS `animation`
declarations that the existing rule at `App.jsx:384` already covers by
selector (`.b3 *`). Sign-off recorded in the Motion Contract's reused-rule
table above. The one place this phase DOES add new reduced-motion-aware
logic is in JavaScript (the `REDUCE_MOTION`-gated `setTimeout` for
MOTION-02's sequencing, item 1 above) — that is new *logic*, not a new CSS
*rule*, and reuses the existing `REDUCE_MOTION` constant rather than
introducing a second `matchMedia` call.
